# F01 — Shareable work queue views

## Candidate handout (release only when selected)

Operations specialists want to send a colleague the queue they are currently viewing. Add a shareable URL representing team, text search, status, priority, sort and page. Reloading or opening the URL in a fresh browser must reconstruct that view. Browser Back and Forward should restore previous views naturally.

Acceptance: missing parameters use sensible defaults; unknown teams/statuses/sorts and non-integer or negative pages cannot break loading. Avoid two independently authoritative copies of query state. Note drafts, selected ticket objects and transient loading/error state stay out of the URL. Define how search typing affects history and what happens when a shared page is no longer valid. Preserve normal filtering and pagination behavior.

Existing architecture: App owns Query, useQueue consumes it, and api.list serializes it. Scope: a URL parsing/serialization boundary plus integration with navigation; no backend change or login. Target 30–45 minutes. Test valid round-trip serialization, malformed parameters, reload, Back/Forward and filtered pagination. Cover URL encoding, empty search, whitespace, repeated parameters, and a deleted/unknown team. Explain normalization choices.

Optional extensions: named local saved views, restore defaults, copy-link action with useful feedback.

## Examiner notes — never release

Check A and B are addressed enough to avoid confounding results. Hint sequence: what constitutes the view; where should the authoritative representation live; how does popstate enter React; which edits deserve history entries? React Router is optional. Do not require a library for a modest parser. Trade-offs: replaceState for rapid typing versus pushState for deliberate navigation, debouncing network work separately from URL state, and normalization without navigation loops. Assess behavior over preferred hook syntax.
