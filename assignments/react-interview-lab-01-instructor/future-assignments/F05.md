# F05 — Reliable note editing

## Candidate handout (release only when selected)

Customer-facing teams require stronger confidence in internal-note editing. The next release must visibly confirm a successful save, preserve the draft after a rejected or unreachable save and make retry possible without retyping. Notes are limited to 4,000 characters. Unknown payload fields and invalid values must be rejected by the API.

Acceptance: the visible success message corresponds to the saved version; editing again clears outdated success feedback. A failed save shows useful feedback while retaining the exact draft. Retrying can succeed, and unrelated updates do not discard text. Define behavior if the candidate closes or changes tickets while a save is pending. Explain which guarantees already exist and which require a change.

Scope is a 25–40 minute reliability improvement and a justified test portfolio. Use pure tests for any extracted validation logic, component/network tests for typing/error/retry behavior, HTTP tests for payload enforcement, and identify one useful end-to-end check. Implement representative meaningful tests rather than maximizing test count. Avoid mocking component internals or duplicating every assertion at every layer.

Existing architecture: TicketDetail local note, api.update HTTP boundary, server PATCH validation and Store persistence. Edge cases: empty notes, exact size boundary, malformed JSON, unmounted editor, double click, delayed confirmation and stale success messages. Optional extensions: revision-based conflicting saves or accessible navigation confirmation for dirty drafts.

## Examiner notes — never release

Some ordinary happy paths are covered already. Ask the candidate to inspect coverage and add value. Helpful prompts: what could a mocked update function conceal; which boundary owns length validation; how can failure/retry be deterministic? Accept an HTTP-level validation test plus one end-to-end flow rather than a giant mocked suite. Do not prescribe MSW if another test boundary offers equivalent evidence. Preserve a draft while reconciling a successful canonical value; do not report success for a stale, superseded save.
