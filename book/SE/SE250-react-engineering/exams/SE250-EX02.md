# Part II — Model Answers and Reasoning

### A01 — Three updates, one result

The handler prints **1** because it closes over the state snapshot of the render that produced it. React processes the queued operations in order. Starting at 1, the first updater produces 3, the direct replacement produces 10, and the last updater produces **20**, which becomes the rendered button text. If the middle replacement is removed, the result becomes **6**: 1 → 3 → 6. The key distinction is replacement versus functional updates and the fact that a state variable does not change in-place inside an existing handler.

The exact ordering here is defined by the queued updates, not by assuming that every state setter immediately renders the component. See SE250-L01.

### A02 — The mutation that silently fails

The array and its first object are mutated directly, then the same array reference is passed back to React. React state should be treated as immutable snapshots. Because the new state value is referentially identical to the previous value, React can skip the update; even if another render exposes the changed object, memoized children or other consumers may still make incorrect assumptions.

~~~tsx
function toggleFirst() {
  setTasks(old =>
    old.map(task =>
      task.id === "a" ? { ...task, done: !task.done } : task
    )
  );
}
~~~

A forced render elsewhere may *reveal* the mutation but does not make this update reliable or correct. It also obscures which operation changed the data. See SE250-L01.

### A03 — The input the user cannot edit

This is a controlled input: its displayed value comes from React's `term` state. The handler logs the attempted new value but never updates that state, so after the change React retains the previous controlled value.

~~~tsx
<input value={term} onChange={e => setTerm(e.target.value)} />
~~~

With `defaultValue`, React supplies only the initial value; the DOM owns subsequent typing. That is a legitimate uncontrolled input when chosen deliberately, but it changes how form data is read, validated and reset. A controlled input is not inherently more correct in every form. See SE250-L01/L03.

### A04 — A component that behaves like an API endpoint

The render function starts a request on every render and displays the string representation of a Promise, not the resolved invoice data. Rendering must stay free of externally visible side effects because React may render more than once, abandon a render, or retry work. Re-rendering can therefore trigger repeated or unnecessary requests. The component also has no coherent loading/error/data lifecycle.

In a client-only application, fetch through a dedicated query layer or an effect with appropriate race handling; render from managed state. In Next.js, a Server Component may await data as part of its server-side rendering path, subject to caching, request scoping and authorization. But it should *await* the data and render its result; it should not stringify the Promise or call a client-only SDK from a server environment.

~~~tsx
// Server-side sketch, not a client component:
async function InvoiceSummary({ accountId }: { accountId: string }) {
  const invoices = await loadInvoicesOnServer(accountId);
  return <p>{invoices.length} invoices</p>;
}
~~~

See SE250-L02/L03/L05.

### A05 — An interval that remembers yesterday

The interval callback was created by the initial render and captures `count = 0`; the empty dependency array means that effect's setup is not rerun for subsequent count changes. The button updates work correctly, but the timer closes over an old snapshot. One simple fix is to make the effect respond to the value that is meant to be logged:

~~~tsx
useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, [count]);
~~~

Each count change clears and recreates the interval, so its one-second cadence resets. If uninterrupted cadence matters, use a carefully synchronized ref (updated to the latest committed value) or a suitable Effect Event pattern rather than introducing stale state or leaving duplicate timers. A ref itself does not cause rendering; it simply allows current data to be read by a long-lived callback. See SE250-L02.

### A06 — The reconnect storm

The object `options` is a new reference every render. The effect depends on that object. A status callback triggers state change → a render → a fresh options object → cleanup/reconnect → potentially a new status. The dependence is on object identity, not on whether `roomId` logically changed.

A direct repair constructs the options *inside* the effect and depends on the stable primitives that actually matter:

~~~tsx
useEffect(() => {
  const connection = connect({ roomId, retry: true }, setStatus);
  return () => connection.close();
}, [roomId]);
~~~

A `useMemo` around options can sometimes work but is not necessary here. Connection setup/cleanup must still be well behaved if a room changes or Strict Mode exercises lifecycle paths in development. See SE250-L02.

### A07 — A cleanup that cleans up nothing

`removeEventListener` requires the same listener function identity that was registered (along with compatible capture options). Two arrow functions that happen to contain the same text are different functions. The cleanup removes nothing.

~~~tsx
useEffect(() => {
  const update = () => setWidth(window.innerWidth);
  update(); // initialize from the actual viewport on mount
  window.addEventListener("resize", update);
  return () => window.removeEventListener("resize", update);
}, []);
~~~

For a production resize-driven layout, consider whether CSS, a media query, or a dedicated external-store approach would be a better source of truth. The essential issue here is subscription lifetime and listener identity. See SE250-L02.

### A08 — The response that wins for the wrong customer

A can overwrite B's data. A's `finally` can also set `loading = false` while B is still pending. An old customer may remain visible during a transition if the UI never clears or differentiates the result's owner. Errors are unhandled, and `finally` can misleadingly signal completion without corresponding current data. The component needs request identity, error state and a deliberate stale-data policy.

~~~tsx
useEffect(() => {
  let active = true;

  setLoading(true);
  setData(null);
  setError(null);

  api.customer(customerId)
    .then(customer => {
      if (active) setData(customer);
    })
    .catch(error => {
      if (active) setError(error);
    })
    .finally(() => {
      if (active) setLoading(false);
    });

  return () => { active = false; };
}, [customerId]);
~~~

This code assumes `setError` has a corresponding state variable. It prevents superseded effects from publishing results; it does not necessarily cancel network traffic. An AbortController is useful if the API supports it. A query library can manage request identity and lifecycle when configured correctly. Test the order A started → B started → B resolved → A resolved, including loading and failure paths. See SE250-L02/L03.

### A09 — One hook, two counters

The counters **do not** share state. Each `Counter` renders separately and each call of `useClicks` obtains its own component-local state cells. A custom Hook shares implementation logic, not a singleton store.

A shared state design could lift `clicks` and the update handler into `App` and pass them as props, or own the state in a common provider/store when distant consumers require it. A context provider distributes a shared owner; merely calling the same custom Hook twice does not create shared state. Prefer lifting state to the nearest appropriate owner before introducing a global abstraction. See SE250-L03.

### A10 — The comparator that lies

The comparator checks only `id`. When `selected` changes but `id` remains the same, React is told the props are equal and may skip rendering; the visual pressed state and text can remain stale. Worse, a changed `onOpen` handler can also be ignored, leaving the row with an outdated callback and potentially stale captured context.

Removing the custom comparator returns to the default shallow prop comparison used by `memo`, restoring correctness with respect to changes in these props. But it does not guarantee optimal performance or fix a parent that passes the wrong data. First verify correctness, then profile; if a custom comparator is truly needed, it must account for every prop that affects behavior, including function props, and justify its maintenance cost. See SE250-L04.

### A11 — Eight booleans for a three-state problem

For a single in-flight save, a discriminated union makes contradictory states unrepresentable. It forces UI rendering to select one coherent branch and simplifies testing:

~~~tsx
type SaveState =
  | { kind: "idle" }
  | { kind: "saving"; requestId: number }
  | { kind: "saved"; savedAt: string }
  | { kind: "error"; message: string };

type Action =
  | { type: "start"; requestId: number }
  | { type: "success"; requestId: number; savedAt: string }
  | { type: "failure"; requestId: number; message: string }
  | { type: "reset" };

function reducer(state: SaveState, action: Action): SaveState {
  if (action.type === "start") {
    return { kind: "saving", requestId: action.requestId };
  }
  if (action.type === "reset") return { kind: "idle" };

  if (state.kind !== "saving" || state.requestId !== action.requestId) {
    return state; // a superseded operation must not win
  }
  if (action.type === "success") {
    return { kind: "saved", savedAt: action.savedAt };
  }
  return { kind: "error", message: action.message };
}
~~~

This reducer assumes `success` and `failure` actions carry `requestId`; reducer calls must be pure. A reducer is useful when multiple events interact with one state machine, but not obligatory for a two-value input. The real skill is modeling valid transitions and superseded work, not choosing `useReducer` for ceremony. See SE250-L03 and CS220-L03.

### A12 — The cache that knows too much about the wrong tenant

The query key does not contain either variable that determines the result. Different tenant/filter requests are incorrectly treated as one cached query. The fix encodes all result-defining parameters in stable, serializable query identity:

~~~tsx
return useQuery({
  queryKey: ["invoices", tenantId, status],
  queryFn: () => api.invoices({ tenantId, status }),
});
~~~

Also consider authenticated account identity and clearing or isolating sensitive cached data on logout or tenant transitions, depending on the app's query-client architecture. Most importantly, **query keys are not authorization**: the server must validate the active user's access to the requested tenant on every applicable request. Do not infer safety from a UI tenant switch. See SE250-L03.

### A14 — The hydration surprise

The `typeof window` check protects against a server-side `ReferenceError`, but not against **different initial markup**. On the server the currency becomes EUR; during the browser's initial hydration render it might read USD. Two different formatted strings break the initial agreement even though the file declares `"use client"`.

One fix uses a stable server-safe initial value and reads localStorage after mounting:

~~~tsx
"use client";
function CurrencyLabel({ amount }: { amount: number }) {
  const [currency, setCurrency] = useState("EUR");

  useEffect(() => {
    setCurrency(localStorage.getItem("currency") ?? "EUR");
  }, []);

  return <span>{formatMoney(amount, currency)}</span>;
}
~~~

This permits an initial EUR → USD update, which may be visible. If that flicker is unacceptable, use a server-readable preference (for instance a validated cookie) to establish the same initial value on both sides, or design a stable placeholder and reveal the value after hydration. Explicitly consider locale/time-zone differences, too. See SE250-L05.

### A15 — Test a race rather than test an implementation detail

Control response order using deferred Promises or a request-mocking layer such as MSW. Render the page, enter query A, verify A is pending; enter query B before A resolves; resolve B and assert B's result appears; then resolve A and assert that B is **still** the visible result. Optionally assert that the pending indicator belongs to the latest request and that a stale rejection does not replace the latest result with an error.

~~~tsx
// Illustrative test outline; mock transport and UI selectors are app-specific.
render(<CustomerSearch />);
await user.type(screen.getByRole("searchbox"), "A");
await waitFor(() => expect(apiRequests).toContain("A"));

await user.clear(screen.getByRole("searchbox"));
await user.type(screen.getByRole("searchbox"), "B");
await waitFor(() => expect(apiRequests).toContain("B"));

resolveRequest("B", [{ name: "Berta" }]);
expect(await screen.findByText("Berta")).toBeVisible();

resolveRequest("A", [{ name: "Alice" }]);
await flushPendingUpdates();
expect(screen.getByText("Berta")).toBeVisible();
expect(screen.queryByText("Alice")).not.toBeInTheDocument();
~~~

In real tests, ensure any debounce timers advance deterministically and all asynchronous updates are flushed via Testing Library / React's supported mechanisms. Assert the visible user contract, not a particular number of effect invocations, Hook calls, or internal state variables. See SE250-L04.

### A16 — The 50,000-row screen

Measure first. Compare network timing and payload size, JavaScript CPU/profiled filter+sort time, React component commit timing, and DOM/layout/paint cost. Check whether every keystroke triggers a global state update, whether sorting mutates inputs, and whether all 50,000 DOM nodes are mounted. A huge list can be slow even with perfect memoization.

A pragmatic progression: reduce work by paginating/filtering server-side where appropriate; avoid rendering invisible rows by virtualization; place urgent input state near the input; make sorting/filtering efficient and memoize **measured** expensive pure work if necessary; defer nonurgent result updates when useful. Debouncing reduces how frequently a search/filter operation is triggered; deferring prioritizes responsiveness but doesn't inherently reduce backend traffic or total work. Virtualization reduces mounted DOM, not data-transfer volume. Moving work to the server changes latency and resource costs, so measure that trade-off too. See SE250-L04 and SE250-L05.

### A17 — Extension: Why the error boundary stays silent

An ordinary Error Boundary catches rendering/lifecycle errors in descendant React component trees. It does **not** automatically catch asynchronous Promise rejections or errors thrown in event handlers. The rejected save must be handled in the event workflow: `try/catch`, explicit mutation loading/error states, appropriate user feedback, and logging/retry policy. Unhandled rejection is not a reliable way to drive fallback UI.

~~~tsx
async function handleSave() {
  setSaving(true);
  setError(null);
  try {
    const saved = await api.saveDraft(form);
    setDraft(saved);
  } catch (error) {
    setError("Could not save. Your draft is still here.");
    reportError(error);
  } finally {
    setSaving(false);
  }
}
~~~

A render-time exception in a descendant component, by contrast, is a normal Error Boundary case. Framework-specific routers and Suspense mechanisms may have additional integration behavior; the generic rule remains that a form submission's rejection is not caught merely because the JSX is wrapped in an Error Boundary. This is an adjacent interview extension.

### A18 — Extension: Build an order editor without building a disaster

**State ownership:** The URL owns addressable navigation such as order ID and selected tab. The server owns canonical order content and stock. A query cache holds read-only client representations keyed by order and identity, with deliberate freshness/invalidation. The editor owns a separate local **draft** with dirty-field tracking; switching tabs should not destroy it. A common trap is copying a refreshed server response into draft state on every render/effect and silently wiping the user's edits.

**Save correctness:** Send an explicit mutation command with a request/idempotency key and, where possible, version/ETag or other optimistic-concurrency precondition to detect colleague edits. A timeout is an *unknown outcome*, not proof of failure. The client should show an uncertain/pending outcome, reconcile with a status/idempotency lookup or refetch, and avoid blind duplicate submissions. On a confirmed save, update/invalidate relevant queries and reconcile the draft/version. On a conflict, show what changed and let the user resolve it instead of overwriting someone else's work.

**Operational quality:** Subscribe/poll for stock changes as needed, but stock display is advisory; availability is checked authoritatively when committing business actions. Keep line-item components keyed by stable IDs, avoid duplicating server data into multiple stores, and structure features so data access and UI behavior can be tested independently. Test unsaved draft preservation, tenant authorization, conflicting concurrent edits, retry/timeout uncertainty, cache invalidation, and fast input behavior for realistic order sizes. For version one, avoid a home-grown event bus, universal Redux-like global state, collaborative CRDT editing, and optimistic claims that an order was committed before confirmation. Start with a straightforward, explainable architecture and add machinery when product evidence requires it. This is an adjacent interview extension.
