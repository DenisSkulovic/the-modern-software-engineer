# SE250 — Course Examination EX01: React Without Superstition

**Course:** React Engineering for Experienced Developers · **Coverage:** SE250-L01–L06, with a Vue-experienced candidate in mind  
**Audience:** Practical full-stack/frontend interviews · **Mode:** Oral reasoning first, code only where genuinely helpful  

The questions are meant to test whether you can debug and design React applications, not whether you recall every Hook API. A strong answer identifies the state owner, the data lifecycle, and an observation that would distinguish competing explanations.

# Part I — Questions

## Round A — Understand the UI's model

### Q01 — The counter that increments once
A click handler performs three state updates using the same expression based on the current `count`, but the UI increments by one rather than three. What is your explanation? How would you make three increments reliable?

### Q02 — The wrong user's form data
A list of editable customer cards is reordered. After the reorder, a card displays one customer's name but retains another customer's unsaved input. What kind of mistake might produce this, and how would you verify it?

### Q03 — The component that resets unexpectedly
A parent changes which customer is selected, but the form continues displaying local state from the previous customer. The developer expects passing new props to reset everything automatically. How do you reason about it?

### Q04 — The effect that fights the component
A component stores `price`, `quantity`, and `total`, then uses an effect to recalculate `total` whenever the first two values change. Sometimes the UI briefly shows mismatched totals. Is this the right use of effects? What would you do?

## Round B — Data and lifecycle

### Q05 — The search result from two keystrokes ago
A user quickly searches for Paris, then Prague. The request for Paris finishes last, overwriting Prague's results. How would you address the race and decide who owns this fetched state?

### Q06 — The same request runs twice in development
A component fetches data from an effect. During local development, the effect's setup appears to run more than expected, while production looks normal. What questions do you ask before trying to suppress the behavior?

### Q07 — Every component invents its own server cache
An application repeatedly fetches the same account data in multiple views, inconsistently updates it after mutations, and sometimes shows two different versions. How would you reorganize data ownership and invalidation?

### Q08 — The filter that vanishes on refresh
Users share a link to a search page, but filters and sorting disappear when the recipient opens it. The state lives only inside React components. What should move where, and why?

### Q09 — The button works, but the page is laggy
Typing into a small search box lags badly only when a large results panel is visible. CPU is high during keypresses. How would you locate the work and choose a fix, rather than blindly applying memoization everywhere?

## Round C — Production choices and diagnosis

### Q10 — The memoized child still renders
A team adds `React.memo` to a child, but it still renders whenever the parent updates. Is React malfunctioning? What would you inspect, and when should you stop optimizing?

### Q11 — HTML arrives, but the page is blank
A product catalogue is rendered primarily in the browser. Its backend is fast, yet users on slow phones stare at an empty page until JavaScript loads. How would you evaluate SPA rendering, SSR, and static generation for this product?

### Q12 — The server and browser disagree
A server-rendered React page shows hydration warnings and briefly replaces some markup when JavaScript loads. What kinds of assumptions could cause this, and how would you investigate without hiding warnings?

### Q13 — A frontend bug with misleading symptoms
A reservation button sometimes submits twice. A developer suggests disabling React Strict Mode and adding a mutable flag in a ref. How would you investigate the actual trigger and protect the business operation?

### Q14 — The unfamiliar React interview codebase
During a technical interview, you're given an unfamiliar React application with a failing test, stale results, and awkward state management. You have 45 minutes. Walk through how you'd investigate and prioritize fixes. What would you deliberately avoid doing?

# Part II — Model Answers and Reasoning

### A01 — The counter that increments once
A React render observes a snapshot of state. Three updates like `setCount(count + 1)` from the same handler may each enqueue the same next value because `count` refers to the same snapshot. Use functional updates, `setCount(c => c + 1)`, for each increment so each update receives the previous queued state. A re-render isn't necessarily immediate after each setter call. Explain batching without treating it as the only cause: the central issue is state snapshot semantics. A stronger design may make the desired next count explicit rather than rely on three identical calls.

### A02 — The wrong user's form data
Unstable list keys, especially array indices in a reorderable list, can cause React to reuse component state for a different logical item. React uses key and component identity to decide which state belongs where. Verify the keys, local input ownership, and whether the bug reproduces on reorder. Use stable unique customer IDs as keys. If form state must follow a particular customer, place it under an identity that survives sorting or manage it by customer ID in a suitable parent/store. Changing the display name doesn't automatically relocate existing component state.

### A03 — The component that resets unexpectedly
Props changing do not inherently reset a component's local state. State persists while React considers it the same component at the same identity/position. Decide whether the form should preserve unsaved edits across customer switching, intentionally reset, or keep independent drafts per customer. A key tied to customer ID can intentionally remount/reset a subtree, but may also discard unsaved changes. Alternatively synchronize or hoist state with care. Avoid using an effect to mirror every prop into local state mechanically. State ownership should encode the product's intended behavior, not be a side effect of reconciliation accidents.

### A04 — The effect that fights the component
`total` is derived synchronously from `price` and `quantity`; storing it as an independent state variable creates the possibility of temporary inconsistency and an extra render. Compute it during render (and memoize only if measurement shows the computation is expensive). Effects are primarily for synchronizing with external systems—subscriptions, network behavior, imperative APIs—not for calculating ordinary values that can be derived from existing React state. If the total is supplied by a server with different business rules, then it is different data with a different owner, and the UI needs to model that explicitly. The distinction is derivation versus synchronization.

### A05 — The search result from two keystrokes ago
The request completion order need not match the input order. An older response overwrites the latest query's result. Use request cancellation where supported, an ignore/sequence guard that only applies current results, or a query library whose cache identity includes search parameters and which manages stale requests. Keep query inputs, results, loading/error states, and request identity coherent. Cancellation can reduce wasted work but doesn't guarantee a remote operation never happened. Consider debounce for UX, but debounce alone isn't a race-proofing strategy. Reproduce with throttled network and deliberately reordered responses.

### A06 — The same request runs twice in development
React Strict Mode can intentionally replay certain setup/cleanup paths in development to expose unsafe side effects, and development behavior can differ from production. First inspect where the request is triggered and whether an effect correctly cleans up or ignores stale work. Don't assume every duplicate request is caused by Strict Mode; it may also be multiple mounts, state changes, or unstable dependencies. Avoid an arbitrary `useRef` "run once" guard that hides lifecycle bugs. For data fetching, prefer a framework/query-cache approach when it manages deduplication and races more reliably. Ensure external mutations are not accidentally initiated by render/effect semantics.

### A07 — Every component invents its own server cache
Distinguish local UI state from server-owned data. Put a shared server-state/query layer in charge of fetching, cache keys, freshness windows, deduplication, errors, and invalidation after mutations. A query identity should include all parameters affecting the response, including tenant/account where appropriate. Keep view-local inputs and ephemeral UI state local rather than globalizing everything. Mutations should update or invalidate the relevant cached views and maintain authorization boundaries. A query cache isn't the source of truth; the server is. Choose tools according to complexity, but establish one consistent ownership model.

### A08 — The filter that vanishes on refresh
Sharable navigation state—search term, filters, sorting, page/cursor where appropriate—often belongs in the URL query string so refreshes and links reconstruct the same view. React should derive the corresponding UI state from that URL or maintain a clear synchronization rule; avoid having two independent sources of truth. Temporary open/closed panels or draft text usually remain local. Validate URL parameters because they are untrusted input and can be malformed. Consider whether a cursor is stable over time and which sensitive data must never appear in URLs. An addressable UI is part of the product contract.

### A09 — The button works, but the page is laggy
Reproduce and profile the specific interaction with React DevTools Profiler and browser performance tools. Determine whether input state is causing a large expensive subtree to render, a costly filter/sort runs synchronously, or layout/paint dominates. Move urgent text-input state close to its owner, avoid unnecessary global updates, memoize expensive pure computations when useful, virtualize enormous lists, or use deferred rendering/transition mechanisms if appropriate. Don't confuse a render count with actual user-visible cost. First establish where the milliseconds go; memoizing every callback adds complexity and may not address the true bottleneck.

### A10 — The memoized child still renders
Memoization typically relies on comparing props, so a parent creating fresh object/function references can cause a memoized child to render. A child can also render because of its own state or context changes. Inspect props, state/context subscriptions, and profiler timings. Stabilizing values or callbacks can help when genuinely needed, but optimize state placement and data flow first. React Compiler may affect the cost-benefit of manual memoization in supported setups, but won't cure incorrect state ownership or expensive algorithms by magic. Stop once measured interaction performance is acceptable; zero renders is not a product requirement.

### A11 — HTML arrives, but the page is blank
A client-rendered SPA may require downloading, parsing, and running substantial JavaScript before meaningful content appears, even when the API is fast. For a public catalogue, server rendering or static/pre-rendered pages can improve the initial content experience and discoverability, but bring caching, infrastructure, freshness, and hydration considerations. Static hotel descriptions may be built or cached broadly; live pricing/availability often needs fresh client/server data and authoritative booking checks. Compare real user timing, device/network constraints, personalization, and update frequency. No rendering model is universally fastest or simplest; the decision depends on what must appear early and stay correct.

### A12 — The server and browser disagree
Hydration assumes the browser's initial render is compatible with server-produced markup. Mismatches can arise from rendering random values, local time/date formatting, browser-only APIs, request-specific data changing between renders, or invalid markup. Reproduce with meaningful diagnostics, identify the first mismatching component, and separate client-only behavior from server-renderable output. Move nondeterministic work to appropriate post-hydration boundaries or provide stable initial data. In modern React/Next.js, distinguish Server Components from ordinary SSR: the former have their own execution model and don't hydrate like Client Components. Suppressing warnings without fixing the disagreement hides a correctness and UX issue.

### A13 — A frontend bug with misleading symptoms
First locate the actual trigger: double-click, two event handlers, duplicated listener, form submit plus button click, retried request, or effect-triggered mutation. Strict Mode does not generally double-invoke user event handlers; blaming it without evidence is risky. Disable controls or debounce where appropriate for UX, but enforce idempotency on the backend for state-changing reservations because clients, networks, and retries are inherently unreliable. Trace requests with correlation/idempotency IDs and write a regression test for the cause. A ref flag can sometimes coordinate local UI work but is not a reliable business correctness boundary across tabs, devices, or network retries.

### A14 — The unfamiliar React interview codebase
Start by reproducing the failing behavior and reading the failing test, current components, state ownership, and data-fetch path. Form a narrow hypothesis before rewriting architecture. Identify whether the symptom stems from stale effects, incorrect keys, duplicate state, query cache identity, or a real backend response issue. Apply the smallest correct fix, add or adjust a regression test, and explain why it works. Communicate assumptions and trade-offs naturally. If time remains, note further improvements. Avoid replacing the whole state library, disabling tests, or spraying `useMemo` everywhere. Interviewers generally learn more from disciplined debugging than from maximal code output.

## Closing perspective

React interviews usually reward the ability to **predict what state belongs to which component, what a render sees, and which external effect can outlive that render**. Knowing those principles matters more than memorizing a shelf of hooks.
