# SE320 — Course Examination EX01: The Backend Has to Survive Reality

**Course:** Backend Services and Asynchronous Processing · **Coverage:** SE320-L01–L03, plus relevant everyday interview extensions  
**Audience:** Experienced full-stack/backend engineer · **Mode:** Independent oral practice or guided discussion  
**Suggested use:** Think and explain out loud, then read the answer section. Skip anything unhelpful; this is learning, not certification.  

The questions deliberately **do not name the mechanism you are supposed to retrieve**. Where several approaches work, defend a reasonable one and its trade-offs. Answers are examples of sound reasoning, not scripts to memorize.

# Part I — Questions

## Round A — Understand the service

### Q01 — The successful booking that returned an error
A customer receives `500` after submitting a reservation. The database contains the reservation and the confirmation email was sent. They click Retry. How might this happen? Where would you investigate and what would you change?

### Q02 — The controller that knows everything
An Express controller parses input, checks permissions, performs MongoDB queries, calls a payment provider, sends email, and maps errors into HTTP responses. It works. Why might you still change it? What should own each responsibility, and how far would you refactor?

### Q03 — A valid request makes a forbidden change
A JSON payload matches your schema, the user is authenticated, and all fields have sensible types. Yet it allows the user to alter another company's asset. What failed, and where should the protection live?

### Q04 — Two requests, one last seat
A booking service checks `remainingSeats > 0`, then decrements the count. Two requests arrive together when one seat remains. How could both succeed, and how would you preserve the business rule?

## Round B — Faster is not always better

### Q05 — The dashboard becomes mysteriously stale
An endpoint drops from 900 ms to 20 ms after you introduce Redis. Customers now see incorrect inventory for several minutes after a booking. What trade-off was made, and what would you adjust?

### Q06 — Fast responses for the wrong customer
A cached API result is extremely fast but occasionally contains another tenant's data. The application enforces authorization correctly when generating the result. How can the leak still happen, and how do you contain it?

### Q07 — The promotion that knocks out the database
A popular item expires from cache and thousands of clients request it simultaneously. The database stalls, despite the cache being designed to protect it. Explain a plausible mechanism and defend mitigations.

### Q08 — Redis goes away for ten minutes
A service uses Redis to speed up reads. Redis becomes unavailable. Should the API keep serving requests, fail them, or return stale information? Explain which details decide your answer.

## Round C — Background work and failure

### Q09 — Move the expensive operation out of the request?
Generating a PDF report takes 45 seconds and occasionally fails. A developer proposes running it in a background job. What benefits would that provide, and what new responsibilities would it introduce?

### Q10 — The email sent twice
A worker sends an email successfully and then crashes before acknowledging its queue message. The job runs again, sending another email. Is the queue broken? How would you limit duplicates and handle the unavoidable uncertainty?

### Q11 — Saved the order, lost the event
A service writes an order to its database and then publishes an `OrderCreated` event. Sometimes the database write succeeds but event publishing fails. Why isn't retrying the HTTP handler an adequate solution? Design a more durable approach.

### Q12 — A job that will never succeed
A queue consumer repeatedly retries a malformed message, filling logs and slowing all other work. What should the processing pipeline do with this job, and what would you make observable?

### Q13 — More workers, slower service
Your team doubles the worker count from 10 to 20. Queue depth shrinks briefly, but database latency rises sharply and overall job completion gets worse. Explain what may have happened and your next decision.

### Q14 — Design a small, trustworthy API
You must expose an endpoint that starts a long-running customer export and lets the frontend track it. Sketch the request/response contract, job lifecycle, storage responsibilities, and how you'd handle repeat submissions or failures. Keep it pragmatic.

# Part II — Model Answers and Reasoning

### A01 — The successful booking that returned an error
The HTTP response describes what the client observed, not necessarily which business effects happened. The reservation could be committed, then email sent, then a later serialization/logging step throws; or the response may fail after the work completes. Inspect request traces, transaction boundaries, the precise exception, and which actions occurred before failure. Make the reservation operation idempotent using a stable request identity, enforce uniqueness where appropriate, and separate durable core state transitions from unreliable notifications. If the email is secondary, deliver it asynchronously with a durable outbox rather than making successful booking depend on SMTP. Do not simply suppress errors; ensure the API can report or reconcile the actual reservation state.

### A02 — The controller that knows everything
The problem is not the line count by itself; it is that unrelated changes and tests must pass through one tightly coupled unit. A practical split is: middleware for transport-wide concerns; controller for HTTP parsing and response mapping; application service for the use-case workflow; domain logic for business rules; data-access boundary for persistence; adapters for payment and email. This permits testing behavior without HTTP or real suppliers and makes transactional boundaries clearer. But avoid creating twelve interfaces for a small feature. Refactor around repeated pain, change frequency, and testability. Keep code organized by feature if that better contains change; a layered architecture is a means, not the goal.

### A03 — A valid request makes a forbidden change
Authentication answers who the caller is; authorization answers whether this caller may perform this specific action on this specific resource. Schema validation cannot decide ownership. The service must derive the tenant/actor from trusted authentication context, not accept a caller-provided tenant as authoritative. Authorize against the target resource and scope the data access accordingly, ideally ensuring the database query itself includes tenant and ownership constraints where appropriate. Return a safe failure without leaking another customer's data. Test cross-tenant cases, including guessed IDs. Authorization may be enforced at several boundaries, but there should be one clear, reliable policy for each operation.

### A04 — Two requests, one last seat
The check and write are separate operations: both requests can read one remaining seat, both decide booking is allowed, and both write success. A transaction alone is not automatically a cure if its isolation and write pattern permit conflicting decisions. A robust design can perform an atomic conditional update such as decrementing only when remaining seats are positive, then verify a row/document was modified. Alternatively use a suitable lock or serializable transaction and retry correctly on conflicts. Also ensure there is a durable reservation identity so a network retry does not consume inventory twice. Define the invariant first: inventory must never become negative or oversold.

### A05 — The dashboard becomes mysteriously stale
The team exchanged freshness for lower latency. A TTL is not a correctness guarantee; it is a maximum reuse policy under ordinary cache behavior. The right change depends on whether the data is advisory or authoritative. Search listings may tolerate slightly old availability, while final purchase/booking must check the source of truth transactionally. For visible freshness, invalidate or version relevant cache entries on writes, choose shorter TTLs if acceptable, or explicitly communicate that availability is provisional. Inspect the cache key, update paths, and distributed invalidation timing. Don't treat a cached displayed count as permission to commit a reservation.

### A06 — Fast responses for the wrong customer
The cache can bypass correct authorization when its key fails to represent information that changes the result. If `/reports/latest` is cached by URL alone, tenant A's result may be returned to tenant B without generating it again. First disable or bypass the unsafe shared cache path, purge sensitive entries, assess exposure, and verify no additional leak. Then design keys around authorization-sensitive dimensions or choose not to share-cache private responses at all; include tenant identity and relevant filters when safe. A request-time authorization check still matters. A cache is another data-serving component and must respect the same isolation guarantees as the origin.

### A07 — The promotion that knocks out the database
A cache stampede occurs when many requests simultaneously miss the same hot key and independently recompute it. Each request may be correct, but the combined load defeats the purpose of caching. Coalesce identical work (single-flight/request collapsing), stagger expirations with jitter, refresh popular keys proactively, or serve bounded stale data while refreshing when acceptable. Put limits on database concurrency and recognize that stale data is unsafe for some operations. Inspect cache hit/miss rate, origin request rate, slow queries, and key-level concentration. Increasing Redis memory would not fix synchronized misses if the expiry policy remains unchanged.

### A08 — Redis goes away for ten minutes
Choose failure behavior per data contract. If Redis is merely an optimization and the database can sustain fallback traffic, serve fresh data from the database with rate limits or bounded concurrency. If traffic would melt the database, degrade or shed lower-priority requests rather than collapsing the source of truth. If the cache contains only advisory public information, stale data may be permissible with clear bounds. If Redis holds essential session state or a rate-limit/coordination function, a fallback could have security or correctness implications and may need fail-closed behavior. Design and load-test the outage mode rather than discovering it during the outage.

### A09 — Move the expensive operation out of the request?
A job lets the HTTP request return quickly, decouples processing from browser timeouts, and allows controlled concurrency and retries. The API might return `202 Accepted` with a job identifier; the frontend polls a status endpoint or listens for updates. New responsibilities include durable job storage, ownership/authorization, job state transitions, progress, output retention, cancellation policy, retries, and cleanup. A queue does not guarantee exactly-once effects. Ensure workers can resume after crashes and that two workers cannot both publish inconsistent results. Keep the initial design modest: a database record, a queue, a worker, and a well-defined status API can suffice.

### A10 — The email sent twice
This is a normal at-least-once delivery failure window: the side effect happened but acknowledgment didn't. Re-delivery is expected. Deduplicate against a stable business event ID and record delivery state durably, but recognize email providers do not always offer atomic deduplication with your database. You can reduce duplicates by making jobs idempotent, using provider idempotency features where available, and reconciling ambiguous outcomes. Depending on the stakes, occasional duplicate informational email may be acceptable; duplicate payment capture is not. State clearly what guarantee is achievable rather than promising magical exactly-once execution across independent services.

### A11 — Saved the order, lost the event
A database commit and a broker publish are two independent durable actions; doing one then the other creates an unavoidable crash window. Retrying the HTTP handler can duplicate the order or create confusing outcomes and may never occur. The transactional outbox pattern writes the order and an event-intent row in the same database transaction. A separate publisher sends pending outbox entries and marks progress, with retries. Consumers must still tolerate duplicate deliveries because publishing and marking sent are not one atomic operation with the broker. Event IDs, versions, and idempotent consumers complete the design. Monitor outbox age and stuck records.

### A12 — A job that will never succeed
Differentiate transient errors (temporary network outage) from permanent errors (invalid payload, unsupported business state). Bound retries with backoff and a sensible deadline; move exhausted or permanently invalid jobs to a dead-letter mechanism or explicit failed state. Include correlation/job IDs, exception classification, attempts, timing, and payload metadata safe for logging. Provide a deliberate replay procedure after a bug fix rather than looping forever. A poison job should not starve unrelated tenants or block the whole queue. Operators should be able to see both the symptom and its effect on queue age and throughput.

### A13 — More workers, slower service
Scaling consumers can overload a shared downstream bottleneck: database connection pools, lock contention, I/O, supplier rate limits, or even the message broker. Throughput rises only until the constrained resource saturates; beyond that, queuing and retries can make useful completion worse. Check worker concurrency, per-worker pool sizes, database wait times/locks, and retry volume. Revert or cap concurrency, add backpressure, and optimize the actual bottleneck. If 20 workers open 20 connections each, that's potentially 400 competing database connections. More workers are not automatically more capacity.

### A14 — Design a small, trustworthy API
A reasonable contract is `POST /exports` returning `202` and an export ID, `GET /exports/:id` returning `queued | running | succeeded | failed` plus permitted progress metadata, and an authenticated download link when ready. Store owner/tenant, request parameters, durable state, attempt history, and output location. Validate permission when creating, checking, and downloading. Use a stable request key or deduplication rule if duplicate submissions are costly; define whether repeats create separate exports. Queue the work durably and ensure worker transitions are safe under retries. Consider expiration and cleanup for potentially sensitive files. SSE is optional for UX, not a requirement for correctness.

## Closing perspective

A successful backend makes **business outcomes** trustworthy despite HTTP errors, cache misses, worker crashes, and retries. If you can explain where truth lives, which operations can repeat, and which observation you would gather next, you're answering at the right depth for a practical full-stack role.
