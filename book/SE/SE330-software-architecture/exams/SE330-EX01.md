# SE330 — Course Examination EX01: Architecture Is the Cost of Change

**Course:** Software Architecture and Evolution · **Coverage:** SE330-L01–L03 and practical senior-level judgment  
**Audience:** Senior full-stack engineer working with real teams and legacy products  

There are deliberately few canonical diagrams to memorize. We want to hear a coherent explanation of trade-offs, constraints, and a plan that can survive ordinary developers and imperfect information. Read Part II after attempting the questions.

# Part I — Questions

## Round A — Boundaries and priorities

### Q01 — The "clean architecture" proposal
A team has a small working Node.js product. A new senior developer proposes five layers, an interface for every class, and strict dependency inversion everywhere. How would you evaluate the proposal without dismissing architecture altogether?

### Q02 — One feature changes twelve files
Adding a discount rule requires editing controller, service, repository, mapper, validator, DTO, shared helper, and several modules. Why is change spreading so widely? What might you reorganize first?

### Q03 — Fast, secure, flexible, cheap
A stakeholder requests a system that is maximally fast, reliable, secure, flexible, and inexpensive. Where do you begin before choosing frameworks, databases, or deployment patterns?

### Q04 — Split the monolith before launch?
A product team of eight developers expects to launch a booking platform in four months. Some engineers demand microservices because "we'll scale later." What would you recommend and what evidence could change your mind?

## Round B — Patterns as decisions

### Q05 — SQL details everywhere
A change from MongoDB to PostgreSQL would require modifications across controllers, business rules, and tests. How would you isolate persistence without pretending the database is irrelevant?

### Q06 — Reuse that created a dependency web
Several teams share a huge `common` package. Every small change forces coordinated releases and occasionally breaks unrelated services. Why isn't this necessarily good reuse, and how would you unwind it?

### Q07 — Three modules disagree about "customer"
Billing, support, and marketing each have a customer object with different required fields and life cycles. Someone proposes one global customer model for consistency. How would you approach this disagreement?

### Q08 — The event-driven rewrite
A synchronous monolith works, but a developer proposes replacing most method calls with events to "decouple everything." What new problems would that introduce, and where might events genuinely help?

### Q09 — The abstraction that only has one implementation
A service interface has one concrete class and is used by one caller. Is the interface valuable? How would you decide whether to keep it?

## Round C — Real software changes over time

### Q10 — The 500,000-line rewrite temptation
A legacy application is difficult to modify. Management proposes freezing features for a year and rewriting everything in a fashionable framework. What risks would you raise and what alternative migration strategy might work?

### Q11 — Refactor or ship?
A feature request touches a notoriously messy pricing module. The proposed fix would take one day; cleaning the module might take three weeks. How do you decide how much refactoring to do now?

### Q12 — Changing a shared database field safely
An old and new version of your service will run simultaneously during deployment. The new version changes how a customer status is represented. How do you evolve the database contract safely?

### Q13 — A boundary that the organization ignores
An application has carefully designed modules, but developers keep importing internal files from other modules to get work done faster. Is the architecture truly modular? What would you do beyond reminding everyone to follow the rules?

### Q14 — Defend an architecture to a CTO
You can improve the performance of a slow dashboard with a cache, read replica, denormalized view, or frontend changes. You only have a week. How do you make a defensible recommendation rather than listing buzzwords?

# Part II — Model Answers and Reasoning

### A01 — The "clean architecture" proposal
Ask what change or testing pain the proposal solves. Layers and dependency rules can isolate unstable infrastructure from stable business policy, but indirection has real cognitive and maintenance costs. A small service with clear feature modules and a few explicit boundaries may be better than interfaces everywhere. Identify which dependencies are likely to change, which business logic needs isolated tests, and where coupling already hurts. Introduce architecture incrementally where it pays for itself, and measure whether developers can understand and change the system more easily afterward. Avoid both extremes: "architecture is pointless" and "purity is always good."

### A02 — One feature changes twelve files
High change propagation often reflects misaligned boundaries: pieces of one business operation are scattered across technical layers or shared helpers. Map the actual change path and determine what can live together as a cohesive feature slice. Keep boundaries where they protect important contracts, but avoid forcing a new business rule to traverse six redundant transformations. The objective is to make common changes local and exceptional changes deliberate. Assess tests and ownership as well; a single large file isn't automatically worse than a web of tiny files. Change coupling, not folder count, is the signal.

### A03 — Fast, secure, flexible, cheap
Translate adjectives into measurable scenarios and constraints. Which operations need low latency? At what volume and percentile? What failure duration is tolerable? What data is sensitive, what regulations apply, and what is the budget/team size? Rank the qualities when they conflict. A design cannot maximize all properties simultaneously. Discuss workload shape, expected growth, data correctness, deployment frequency, and operational staffing before picking technologies. Choose reversible decisions where uncertainty is high, and validate assumptions with simple prototypes or measurements. Architecture begins with trade-offs that matter to the product, not a favorite stack.

### A04 — Split the monolith before launch?
A modular monolith is often the default for a small team with an approaching launch: one deployment and database transaction boundary, but clear internal modules and ownership. Microservices add network failures, distributed transactions, deployment and observability complexity, and cross-service contracts. They earn their cost when independent teams, very different scaling needs, isolation requirements, or organizational constraints justify them. Define module boundaries now so later extraction is feasible. Ask which capability truly needs an independent lifecycle and whether the team can operate distributed infrastructure responsibly. Scaling later is a valid concern, not an automatic reason to incur all distributed costs today.

### A05 — SQL details everywhere
Define application/domain operations in terms of business needs rather than exposing database query shapes to every caller. Put persistence-specific code behind coherent repository or data-access adapters; inject dependencies where testing and substitution benefit. Keep transactions and query capabilities honest: swapping MongoDB for PostgreSQL may still require rethinking schemas, consistency, and performance, not changing one class name. Avoid an excessively generic repository that hides powerful database features or forces expensive abstractions. The architecture should isolate avoidable coupling while acknowledging that persistence is part of the system's design.

### A06 — Reuse that created a dependency web
Shared code can create tight **release coupling**: one library's version or contract becomes everyone's problem. A monolithic `common` package may contain unrelated concerns and unstable helpers with broad dependencies. Identify genuinely stable cross-cutting utilities versus business logic that belongs to one domain. Split coherent packages where there is clear ownership, reduce unnecessary imports, and prefer explicit API contracts over sharing internal models between deployable services. Version backward-compatible interfaces carefully; sometimes duplication is cheaper and safer than forcing unrelated teams to coordinate. Reuse isn't free when it multiplies the cost of every change.

### A07 — Three modules disagree about "customer"
Each domain may legitimately mean something different by "customer": a billable legal entity, a support contact, or a marketing audience. A single universal entity often becomes a bloated compromise with ambiguous ownership. Clarify each domain's language, invariants, and lifecycle; create a clear translation or integration contract at the boundary. Shared identifiers may connect records without forcing identical internal models. This is the practical value of bounded contexts, whether in a monolith or independent services. Favor explicit contracts over a universal canonical object that nobody fully owns.

### A08 — The event-driven rewrite
Events decouple the sender from immediate consumers in time and enable asynchronous projections, but introduce eventual consistency, duplicate delivery, ordering, schema evolution, observability, and operational burden. They are often useful for email, analytics, search indexing, and workflows that don't need a synchronous answer. Core invariants that must succeed or fail together may remain easier inside one transaction and synchronous module call. Decide what fact an event represents, who owns it, who replays it, and what happens when consumers are down. "Event-driven" isn't a substitute for clear responsibilities; it makes some coupling less direct while creating new contracts.

### A09 — The abstraction that only has one implementation
One implementation doesn't automatically make an interface pointless: it may isolate a costly dependency, capture a stable domain contract, or enable focused testing. But if the interface merely repeats a method signature and doesn't separate responsibilities, it is ceremony. Assess change likelihood, dependency direction, testability, and the cognitive cost of navigating additional files. Mocking ease alone isn't always a strong reason; a simple real implementation or local function may be easier to test. Keep abstractions whose boundaries tell a useful story, and remove ones that only promise hypothetical flexibility.

### A10 — The 500,000-line rewrite temptation
Big rewrites risk losing undocumented behavior, introducing fresh bugs, stalling product delivery, and underestimating migration/data compatibility work. Inventory actual hotspots and user-visible pain; add characterization tests around fragile behavior and create observability where missing. Incrementally replace a well-bounded feature or route behind a stable interface (a strangler-style migration), measuring equivalence and keeping rollback possible. Sometimes a rewrite is justified when the old system is truly unmaintainable or technology constraints block essential requirements, but demand evidence and a migration plan. Avoid treating line count or age as proof that software is worthless.

### A11 — Refactor or ship?
Consider how often the module changes, the current defect risk, how easily a small improvement can be verified, and the opportunity cost of delaying delivery. A focused preparatory refactor—with tests and clear scope—may make the requested feature safer. A three-week overhaul during an urgent change could introduce more risk than it solves. Leave the code slightly better than you found it without pretending every visit requires renovation. If technical debt repeatedly slows delivery, make the accumulated cost visible and propose a separately justified investment. Refactoring is an economic decision tied to future change.

### A12 — Changing a shared database field safely
Use expand-and-contract compatibility. Add the new representation without immediately removing the old one, deploy code that can understand both, backfill or dual-write where necessary, migrate reads, and remove the old representation only after old binaries and consumers are gone. Consider delayed jobs, caches, readers, and rollback—not only web instances. Track migration completeness and design it so partial runs can resume safely. Apply stricter constraints last when historical data is compatible. Database schema is a deployed contract with multiple versions in flight, not a private implementation detail of the latest commit.

### A13 — A boundary that the organization ignores
A module boundary is weak if any consumer can bypass it with imports. Investigate why developers need to reach inside: missing public capabilities, inconvenient APIs, time pressure, or unclear ownership. Fix the API and workflow friction first, then enforce acceptable dependency directions through package boundaries, build tooling, dependency tests, or automated lint rules. Review exceptions deliberately rather than normalizing them. Architecture must be technically and socially sustainable. A rule that continually gets bypassed is evidence either that the design is poorly aligned or that enforcement is missing—often both.

### A14 — Defend an architecture to a CTO
Start by measuring where time is spent: network round trips, database scans, lock waits, backend processing, or client rendering. Then choose the smallest intervention addressing the dominant cost. A cache helps repeated expensive reads if staleness is acceptable; a replica may isolate read load but adds lag and may not fix bad queries; a denormalized view improves costly composition but creates synchronization obligations; frontend changes can remove request waterfalls or excessive rendering. State the assumptions, a one-week experiment, expected benefit, failure modes, and rollback plan. The CTO needs a decision with evidence and risk, not a catalogue of patterns.

## Closing perspective

Architecture is the practice of **making important changes cheaper and important failures safer**, under real organizational constraints. A pragmatic explanation beats a diagram of fashionable layers.

**Course touchpoints:** SE330-L01 (qualities and boundaries), L02 (patterns, contexts, modularity), L03 (legacy evolution and refactoring). Cross-course extensions: performance diagnosis and migration operations.
