# Part I — Questions

## Foundations: Explain the invisible contracts

### Q01 — One URL, several different audiences

Consider `https://shop.example.com/orders?status=open#recent`. Which parts matter to DNS, to the network connection, to the HTTP server, and to the browser itself? Which part normally is not sent in the HTTP request? Why is it risky to assume anything in a URL is confidential?

### Q02 — One port, thousands of conversations

A server listens on TCP port 443 and handles thousands of clients simultaneously. How can all those connections use the same server port? Explain the role of the four-tuple, ephemeral client ports, the handshake, and the distinction between a listening socket and an accepted connection.

### Q03 — Two uses of an ETag

A client fetches a document, receives an ETag, and later makes another GET. Explain how conditional requests can save bandwidth. Then explain how a *different* conditional request can prevent two administrators from silently overwriting each other's changes. What would a `304` or a `412` mean in these situations?

### Q04 — DNS failed, but how?

A hostname lookup produces no usable address. Is that one kind of error? Distinguish a nonexistent name, an existing name with no address record of the requested type, and a DNS lookup that failed because the resolver could not obtain a trustworthy answer. What does negative caching change?

### Q05 — When bandwidth is not the limiting window

A long-distance TCP transfer underuses an otherwise fast connection. Explain the difference between receiver flow control and network congestion control. How does the bandwidth–delay product help reason about the amount of data that must be in flight? Why can adding large buffers sometimes make interactive traffic *worse*?

### Q06 — VPN connected, database unreachable

A developer connects successfully to the corporate VPN, but requests to a database address still go to a local virtual network. How can this happen when the VPN itself is healthy? What would you inspect, and why can “the route exists” be insufficient to prove the intended path is used?

## Applied engineering: Design and interpret

### Q07 — Public load balancer, private application

A service is reachable over HTTPS from the internet, yet its application instances have no public IPv4 addresses. Describe a plausible architecture. Now suppose the private application also needs outbound internet access. Which additional decisions become necessary, and why does a route through an internet gateway alone not automatically solve it?

### Q08 — The supplier suddenly rejects your traffic

A payment supplier begins rejecting requests after a cloud infrastructure change. The application code, hostname, and TLS certificate did not change. The supplier enforces an outbound-IP allowlist. What network-level change could explain the incident, and how would you verify and prevent its recurrence?

### Q09 — Trust, keys, and future secrecy

Explain how TLS can use a certificate to authenticate a server while using ephemeral key agreement to establish symmetric session keys. What is forward secrecy, why does merely encrypting traffic not identify the correct peer, and when might mutual TLS be useful?

### Q10 — Choosing and draining load-balanced targets

Contrast layer-four and layer-seven load balancing. What changes when balancing individual connections versus HTTP requests? Why might a health check return success even while users are failing, and why does graceful connection draining matter during deployments?

### Q11 — The CDN that attacks its own origin

A popular cacheable response expires, and thousands of clients request it nearly simultaneously. The CDN is supposed to reduce origin load, but the origin CPU suddenly spikes. Explain this failure mode and several ways to contain it without serving unsafe or indefinitely stale responses.

### Q12 — The new transport has new risks

A team enables HTTP/3, but some customers still use HTTP/2. Explain how that is possible even when both are supported. What role do QUIC, UDP, protocol discovery, and fallback play? Also explain why accepting certain state-changing requests in 0-RTT early data deserves special care.

### Q13 — Three ways to deliver progress

You are building a dashboard for background security scans. The browser needs to see progress events; someday it may also send live commands. Compare polling, server-sent events, WebSockets, and gRPC streaming. Which would you start with, and what does the chosen transport *not* solve for you?

### Q14 — The receiver stops reading

A service streams a large response to a slow client. Its network send buffers fill, yet the application keeps generating data and its memory consumption grows. Explain the backpressure chain, why a stream is not an infinite pipe, and what a correct streaming implementation should do.

## Production cases: Draw conclusions from limited evidence

### Q15 — Connections that refuse to disappear

A Node.js service experiences a sudden growth in `CLOSE_WAIT` sockets. Another incident shows many `TIME_WAIT` sockets. Are these the same problem? Explain what each state suggests, how a TCP `FIN` differs from a `RST`, and what evidence you would seek before tuning operating-system parameters.

### Q16 — The incident dashboard says “average is fine”

A production service's average request latency barely changed, but a noticeable fraction of users now experience five-second failures. Some regions are more affected than others. Describe a useful investigation that considers percentiles, error rates, DNS, route and transport conditions, intermediaries, and application timing. Which comparisons would reduce uncertainty fastest?

### Q17 — Extension: Everybody retries

A browser retries a failed call twice, the API gateway retries it twice, and a service client retries it twice. During an outage, why can this design amplify the load instead of healing the system? Describe a more defensible approach to retries and deadlines, especially for state-changing operations.

### Q18 — Extension: REST works, gRPC fails through the proxy

Two internal services communicate successfully through a corporate reverse proxy using ordinary REST calls. After one endpoint is replaced with gRPC, calls fail or hang through the same proxy, although direct connections work. What protocol capabilities and intermediary behavior would you investigate before rewriting application logic?

# Part II — Model Answers

### A01 — One URL, several different audiences

The scheme `https` establishes the intended secure HTTP access. The hostname `shop.example.com` participates in DNS lookup, endpoint selection, HTTP authority, and TLS hostname verification. The connection uses an IP address, port, and an appropriate transport; the server's HTTP routing cares about the path `/orders` and query `status=open`. The fragment `#recent` is interpreted by the browser and normally is not transmitted as part of the HTTP request target.

A URL is a set of instructions for different layers, not a single opaque address. HTTPS encrypts the path and query in transit against ordinary network observers, but those fields can still appear in browser history, server and proxy logs, analytics, copied links, and referrers depending on policy. DNS queries can reveal hostname information; the fragment can expose information to client-side scripts. Never use URL placement alone as a secrecy guarantee. For browser-origin rules, scheme, hostname, and port matter together.

### A02 — One port, thousands of conversations

A TCP connection is usually identified by the combination of source IP, source port, destination IP, and destination port, plus the transport protocol. Many clients can connect to the same server IP and port 443 because their source addresses or ephemeral source ports differ. The server has a listening socket on 443, while accepted connections are distinct sockets with separate transport state.

The three-way handshake establishes the connection's initial sequence-number state; the server accepts usable connections for application handling, subject to backlog, resource, and scheduling constraints. A server can be listening yet fail under overload because its connection queues or application workers cannot keep up. Client ephemeral-port exhaustion or too many open file descriptors may cause problems even when the server code is otherwise healthy. A port number alone is not a unique connection identifier.

### A03 — Two uses of an ETag

An ETag identifies a particular representation version according to the server's chosen validator scheme. After caching a response, the client can send `If-None-Match` on a later GET. If the selected representation has not changed, the server can answer `304 Not Modified` without sending the full representation body; the client reuses its stored copy. This is cache revalidation, not evidence that the server returned no useful information.

For concurrent editing, the client can send `If-Match` with a known strong validator on a modification request. If another editor changed the resource first, the precondition fails; the server can return `412 Precondition Failed` instead of silently overwriting the newer version. This is optimistic concurrency control expressed through HTTP. `304` and `412` have different purposes: one says “reuse your cached representation,” the other says “the state no longer meets the condition for this write.”

### A04 — DNS failed, but how?

`NXDOMAIN` means the queried domain name does not exist according to the DNS response. `NOERROR` with no records of the requested type may mean the name exists but has no such address records, commonly called a no-data result. `SERVFAIL` indicates the server could not complete the query successfully; causes include upstream resolution trouble and DNSSEC validation failures. Transport timeouts and client resolver errors are additional distinct failures.

Recursive resolvers can cache negative answers for a bounded time under DNS rules, so creating a previously missing name does not necessarily make every client resolve it instantly. Diagnose by comparing the configured recursive resolver with appropriate authoritative answers and examining response codes, records and timing. An absent AAAA answer is not the same as an absent domain. Saying “DNS is down” conceals distinctions that materially change the fix.

### A05 — When bandwidth is not the limiting window

TCP receiver flow control limits the sender according to how much data the receiving endpoint can buffer and consume; congestion control regulates how much data the sender injects based on the network's estimated capacity and congestion signals. The effective amount in flight is constrained by both, along with other limits. A long RTT requires enough unacknowledged data in flight to keep a high-capacity link busy.

The bandwidth–delay product roughly estimates that amount: target bandwidth multiplied by round-trip time. A sender with too small a usable window cannot reach the line rate even if the physical link is fast. Buffers can absorb bursts, but excessively deep queues add delay under load—bufferbloat—damaging interactive traffic and increasing tail latency. Inspect RTT, loss, retransmits, receive-window constraints, congestion behavior, and queueing rather than treating the advertised link rate as achieved application throughput.

### A06 — VPN connected, database unreachable

A functioning VPN tunnel only confirms the tunnel exists; it does not guarantee the operating system chooses it for the database's destination. A more specific local or virtual-network route may win via longest-prefix matching, especially when Docker, VPN, office, and home networks overlap. The machine may send traffic to the wrong interface while reporting that the VPN is fully connected.

Inspect the effective route lookup for the *specific destination*, not just the presence of a VPN route. Compare prefix lengths, routing tables or policy-routing rules, selected source address, and interface. If the route is correct, separately test next-hop reachability, firewall policy, server listeners, and the return path. ARP or Neighbor Discovery handles local-link delivery after routing has selected a next hop; neither repairs an incorrect network-level decision. A green VPN icon is not a routing proof.

### A07 — Public load balancer, private application

A public load balancer can have internet-facing listeners and forward traffic to application targets on private addresses inside a VPC. Users reach the load balancer, not each instance directly. The instances can be deliberately inaccessible from the public internet while still receiving traffic from the trusted edge, with security policies limiting allowed sources and ports.

Outbound internet access is a separate problem. A private IPv4 instance without a public address typically needs a route through an appropriate NAT service or egress proxy; an internet gateway route alone doesn't perform outbound source NAT and cannot make a private address internet-routable. The gateway must itself have a workable public egress path, and security groups, network ACLs, DNS, partner allowlists, and return routing still matter. IPv6 deployments can use globally routable addresses with explicit egress-only or firewall rules, demonstrating that “private” and “NAT” are not identical concepts.

### A08 — The supplier suddenly rejects your traffic

The application may now leave the cloud through a different NAT gateway, egress proxy, region, availability zone, public address allocation, or service-mesh egress path. The supplier sees the **translated public source IP**, which is not necessarily the instance's private IP and may change after an infrastructure migration. A correct API hostname and certificate do not establish that the supplier accepts the caller's source network identity.

From the actual workload, determine the observed public egress address and compare it with the supplier's allowlist and the infrastructure's routing/NAT configuration. Inspect supplier rejection logs and cloud flow logs if available. Prevent recurrence through a documented stable egress architecture, controlled IP changes, explicit allowlist coordination, deployment tests, and monitoring. For high availability, recognize that multiple availability zones can require multiple egress addresses and thoughtful failover planning.

### A09 — Trust, keys, and future secrecy

In a modern TLS handshake, the server presents a certificate binding an identity to a public key under a trusted certificate authority's signature. The server proves possession of the corresponding private key and authenticates the handshake. Ephemeral Diffie–Hellman key agreement allows the peers to derive shared secrets without sending the final symmetric traffic key over the wire. Symmetric authenticated encryption then protects application data efficiently.

Encryption without authenticated identity could protect the traffic *to an attacker* who substituted themselves as the endpoint. Forward secrecy means later compromise of the server's long-term certificate key does not, by itself, allow an observer to decrypt previously recorded sessions that used suitable ephemeral key agreement. Mutual TLS extends certificate-based authentication to the client too; it can help authenticate services or devices, but it does not replace fine-grained application authorization or lifecycle management of identities and keys.

### A10 — Choosing and draining load-balanced targets

Layer-four load balancing mainly distributes transport-level connections using addresses, ports, and protocol state. Layer-seven load balancing understands HTTP details and can route by host, path, headers, or other application properties; it may choose targets on a request or stream basis. Distribution policy, connection persistence, session affinity, and backend connection pools therefore affect actual traffic patterns differently.

A health check may only verify that a process answers `/health`, even while its database, queue, or essential dependency is failing. Conversely, making every transient downstream dependency a hard liveness requirement can trigger cascading restarts. Distinguish readiness to serve traffic from liveness of the process. During deployment, stop sending new work to an old target, allow in-flight requests and streams to drain within bounded time, and only then terminate it. Otherwise a perfectly healthy rolling deployment can manufacture user-visible resets.

### A11 — The CDN that attacks its own origin

This is a cache stampede or thundering herd: when a popular object expires, many simultaneous misses trigger duplicate origin work. The cache normally dampens load, but synchronized expiration briefly turns it into a load multiplier. This can overload the origin precisely when demand is high.

Possible controls include request collapsing or single-flight fetching per cache key, stale-while-revalidate for data that tolerates bounded staleness, randomized expiration times, origin shielding, and origin-side admission control. Monitor hit rates and origin concurrency. Differentiate truly public resources from personalized or safety-critical responses; do not make private data shared-cacheable in order to improve hit rate. Staleness is a product consistency decision, not merely a performance optimization.

### A12 — The new transport has new risks

HTTP/3 uses QUIC over UDP, but a client needs to learn that the server supports it and successfully communicate over that path. Discovery mechanisms such as Alt-Svc, client implementation choices, intermediary capabilities, firewall restrictions, and network conditions can lead one client to use HTTP/3 while another uses HTTP/2. Fallback is a feature, not necessarily an outage.

QUIC integrates encryption and transport setup, and can support resumed sessions with 0-RTT early data. Early data can be vulnerable to replay under relevant threat models. A non-idempotent mutation—such as creating a payment—should not be assumed safe to execute merely because the transport delivered it quickly. Restrict or reject early data for replay-sensitive operations, or enforce suitable application-level idempotency and replay defenses. Lower handshake latency does not remove business invariants.

### A13 — Three ways to deliver progress

Polling is simple and robust, but repeatedly asking for unchanged state wastes requests and can introduce visible delay. Server-sent events are well suited to one-way, server-to-browser event streams over HTTP, often with convenient reconnection support. WebSockets provide bidirectional messaging and a persistent connection, useful when the dashboard must send interactive commands, though the operational model is more involved. gRPC streaming is compelling for typed service-to-service interfaces, but browser integration and intermediary support require additional decisions.

For a straightforward browser progress feed, start with ordinary polling if updates are infrequent; otherwise SSE is often sufficient. Choose WebSockets if bidirectionality and latency requirements truly justify them. None of these transports guarantees durable event delivery, replay after disconnection, authorization, valid state transitions, or safe handling of slow consumers. A scan-status snapshot endpoint or resumable event protocol may still be necessary.

### A14 — The receiver stops reading

When a consumer reads slowly, the receiver's buffers fill, TCP flow control slows the sender, and the sender's operating-system or transport buffers eventually stop accepting unlimited output. That pressure must propagate into the application: a streaming writer should wait for drain/readiness signals rather than generating unbounded chunks into its own heap.

Bound application queues, respect writable-stream backpressure, cancel work when consumers disconnect, and impose timeouts or limits for perpetually slow clients. Intermediary proxies may buffer data or impose their own flow control, so backpressure can cross several layers. A stream means data is produced and transmitted incrementally; it does not create infinite memory or guarantee immediate delivery to the browser. If the upstream computation cannot be slowed, intentionally choose a bounded buffer, sampling, dropping policy, or durable queue appropriate to the product's correctness requirements.

### A15 — Connections that refuse to disappear

`CLOSE_WAIT` typically means the local TCP stack has received a peer's orderly close (`FIN`), but the local application has not completed its own socket close. Growing `CLOSE_WAIT` counts can indicate leaked sockets or application lifecycle bugs. `TIME_WAIT` appears after certain orderly-close sequences so a TCP endpoint can absorb delayed segments and prevent confusion with a newly reused connection tuple; large numbers can be normal under high connection churn, though they may expose capacity or reuse issues.

A `FIN` participates in an orderly half-close of the byte stream; a `RST` aborts a connection and signals a reset rather than completing that orderly shutdown. Inspect which process owns the sockets, closure timing, error handling, connection-pool behavior, and traffic rates. Changing OS timeout settings without understanding whether the problem is an unclosed application socket or expected churn may hide symptoms while creating worse correctness problems.

### A16 — The incident dashboard says “average is fine”

Averages hide tails. Segment requests by region, endpoint, client type, address family, time window, and backend target; inspect p95/p99 latency, error rate, retries, timeouts, and volume, not only the mean. A five-second tail could reflect packet loss and retransmission, queueing, a slow CDN-to-origin hop, an application timeout, or a small subset of overloaded targets.

Use browser and client timing where available, trace IDs across intermediaries, CDN cache/origin metrics, and endpoint-specific transport observations. Compare one affected and one unaffected client on the same operation: what address did each resolve, which CDN/region served it, was a connection reused, and where did their timelines diverge? Then test hypotheses specifically. A good diagnosis narrows a boundary before proposing a fix; “CPU is normal” is not enough to rule out tail failures.

### A17 — Extension: Everybody retries

Retries multiply. If several layers each issue their own retries, one original operation can fan out into many backend attempts, especially if failures take time and every layer assumes the next will recover. Under overload, these extra attempts consume scarce capacity, delay real recovery, and create a feedback loop. Retrying a non-idempotent operation can also duplicate business effects.

Prefer one well-defined layer responsible for retries, bounded attempts within a shared end-to-end deadline, exponential backoff with jitter, and explicit retryability rules. Add circuit breaking or admission control when appropriate, observe retry rates, and use idempotency keys and reconciliation for state-changing requests. Do not blindly retry on every HTTP status or network exception. The fact that a request *might* succeed on attempt two is not proof that uncoordinated retries are safe at system scale.

### A18 — Extension: REST works, gRPC fails through the proxy

Ordinary gRPC commonly relies on HTTP/2 framing and trailers, plus a precise content type and streaming semantics. A reverse proxy that handles HTTP/1.1 REST correctly may not support the necessary HTTP/2 behavior end to end, might downgrade the upstream connection improperly, mishandle trailers, buffer streams, or terminate them with unsuitable idle or request timeouts. TLS ALPN negotiation and proxy configuration may matter too.

First compare direct and proxied calls while inspecting negotiated protocol versions, TLS termination points, request/response headers, trailers, upstream protocol selection, buffering settings, and timeout logs. Distinguish gRPC from gRPC-Web, which exists partly because browser and proxy capabilities differ. A working REST request proves some HTTP exchange succeeded; it does not establish that an intermediary preserves all the transport and streaming capabilities required by gRPC. Rewrite application code only after the protocol path is understood.
