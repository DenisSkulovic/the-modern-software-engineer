# CS230 — Course Examination EX01: Follow the Boundaries

**Subject:** Computer Networks and Web Protocols  
**Coverage:** The complete CS230 course, L01–L11, with two clearly marked adjacent extensions  
**Style:** Independent oral-practice paper for a practical full-stack/backend engineer

# Part I — Questions

## Foundations: Make the machinery intelligible

### Q01 — A webpage is not a single request

A customer opens a hotel page. The backend handler takes 40 milliseconds, yet useful content appears after four seconds. Narrate the major boundaries between the address bar and the displayed page. Which stages can be skipped or reused, and why is the backend timing not a contradiction?

### Q02 — More bandwidth, still slow

A dashboard makes eight dependent API calls to a server with a 180-millisecond round-trip time. Each response is small. The team proposes upgrading the connection from 100 to 1,000 megabits per second. Would that noticeably fix the perceived delay? What would you investigate or redesign first?

### Q03 — Two countries, two destinations

After a DNS migration, users in one country reach an old deployment, while users elsewhere reach the new deployment. The authoritative DNS records are now correct. Explain how both observations can be true. What should the team have done before the cutover, and how would you investigate now?

### Q04 — The route that wins

A machine has routes for `10.0.0.0/8` via a VPN, `10.20.0.0/16` via a corporate router, and `10.20.18.0/24` via a local interface. Where does traffic for `10.20.18.7` go, and why? What is the difference between choosing a route and finding the link-layer address of the next hop?

### Q05 — Why one write becomes three reads

A Node.js client sends one JSON object using one call to `socket.write`. The TCP server receives it in three `data` events; on another attempt, two objects arrive together in one event. Is TCP malfunctioning? How should a correct application handle this?

### Q06 — The payment response disappeared

A client sends `POST /reservations`, times out, and is about to retry. Does the timeout prove that the reservation failed? How do HTTP method semantics and application-level idempotency help you make this operation safe?

## Working engineering judgment: Connect the layers

### Q07 — A private service cannot call its supplier

An application in a cloud private subnet can reach its database but times out when contacting a payment provider on the public internet. List the independent network conditions necessary for outbound connectivity. Where do routes, NAT, security groups, and the supplier's IP allowlist fit?

### Q08 — Chrome succeeds; Node.js distrusts the endpoint

The same HTTPS endpoint opens in a browser but fails certificate validation in a Node.js worker. What exactly is TLS trying to establish? Give plausible causes for the disagreement and a diagnosis plan that does not disable certificate verification.

### Q09 — HTTP/1.1, HTTP/2, HTTP/3

Compare the three HTTP generations in terms of connection use, multiplexing, transport, and behavior under packet loss. Why is “HTTP/3 is always faster” an unjustified conclusion?

### Q10 — The response came from somewhere else

A customer receives a `200 OK` containing another customer's booking data. The origin service has no log entry for the request. Explain how this can occur through a CDN or reverse proxy, what you would inspect first, and what constitutes a safe caching policy for authenticated data.

### Q11 — Streaming that arrives all at once

A backend emits a progress update every second. Locally, the browser receives them immediately; in production, nothing appears for 30 seconds and then every update arrives together. What failure modes fit this pattern? How would you decide between server-sent events and WebSockets for a one-way progress feed?

### Q12 — Who can you trust behind a load balancer?

An HTTPS load balancer terminates TLS and forwards HTTP to an internal application. What security boundary has changed? What should the application know about the original scheme and client address, and why must it not blindly trust arbitrary forwarded headers?

### Q13 — The first request after idle fails

An API's first call after several minutes of inactivity often fails with `ECONNRESET`; an immediate retry succeeds. What is a plausible explanation involving connection pooling, how would you test it, and why might automatic retries still be dangerous?

## Production forensics: Diagnose without guessing

### Q14 — An edge 504 with no application trace

A CDN reports `504 Gateway Timeout`, but your Node.js application has no corresponding request log. A teammate wants to increase the database timeout. What do you investigate first? Name observations that would distinguish upstream reachability, unhealthy targets, and application slowness.

### Q15 — Large requests vanish in a VPN

Small API calls work, but sufficiently large uploads hang only when the client uses a VPN. A developer suspects a bug in the upload handler. Offer at least two competing hypotheses, including a network-level one. What test results would help distinguish them?

### Q16 — The IPv6-shaped outage

A service has both A and AAAA DNS records. Some clients connect reliably while others hang or experience long delays; forcing IPv4 often succeeds. What are the likely boundaries to examine, and why is a successful IPv4 test not proof that the service works for everyone?

### Q17 — Extension: `curl` succeeds, browser JavaScript fails

A backend endpoint answers `curl` with HTTP 200, but a frontend from a different origin cannot read the response. The browser console reports a CORS error. Is this evidence that the network or TLS is broken? Explain the browser's extra enforcement boundary, including when a preflight is involved.

### Q18 — Extension: The same service fails only in Kubernetes

A containerized worker can call an external API from a developer laptop but cannot call it from a Kubernetes Pod. The hostname resolves inside the Pod. One colleague says “DNS works, so it must be the application”; another says “ping fails, so Kubernetes networking is broken.” Evaluate both claims and propose a short investigation strategy.

# Part II — Model Answers

### A01 — A webpage is not a single request

A browser interprets the URL, checks state it already has, and may use its cache or a service worker. When a network request is needed, DNS may resolve the hostname; routing carries packets to the relevant endpoint; a transport connection and often TLS enable communication; a CDN or proxy may answer or forward the request; the application may generate a response. The browser still has to parse HTML, retrieve dependent resources, execute JavaScript, perform layout, and paint. These operations can overlap, and some are absent on reused connections, cached responses, or client-side navigation.

Forty milliseconds measures one backend handler, not the whole navigation. Diagnose with a browser waterfall, navigation/resource timing, time to first byte, rendering milestones, CDN/proxy timing, and request IDs. Ask where the missing four seconds actually went before blaming the database. A surprisingly fast backend can coexist with a slow user experience.

### A02 — More bandwidth, still slow

Bandwidth determines how quickly substantial amounts of data can be transmitted; round-trip latency determines how long request-and-response interactions take. Eight truly dependent round trips at 180 milliseconds already imply roughly 1.44 seconds of network waiting before application and browser work, even for tiny responses. Ten times more capacity barely changes that fixed dependency cost.

Look for unnecessary serial requests, frontend dependency chains, repeated authentication or connection setup, distant regions, and slow intermediate services. Parallelize independent calls, batch related data, or reshape the API to return the data the screen needs together. Bandwidth upgrades matter when the bottleneck is transferring enough bytes, not merely traversing long round-trip dependencies. This is why “fast network” needs both a throughput and a latency measurement.

### A03 — Two countries, two destinations

DNS is distributed and cached. The authoritative records can point at the new endpoint while recursive resolvers elsewhere still legitimately retain the previous answer until its remaining TTL expires. Clients may also use different resolvers, address families, cached CNAME chains, or geographic routing. A record update is not an instantaneous global instruction. Negative responses can also be cached.

A safer migration lowers relevant TTLs sufficiently *before* the change, waits for old cached values to expire, keeps the old target functional during overlap, monitors traffic from both destinations, and has a rollback plan. During the incident, compare affected clients' actual DNS results with their configured recursive resolver and the authoritative answers; examine the full resolution path and confirm which IP each request used. Don't conclude that a correct authoritative record invalidates client observations.

### A04 — The route that wins

The destination `10.20.18.7` matches all three prefixes, but the `/24` is the most specific. Under normal longest-prefix matching, the local interface route wins, even if that is the *wrong* path for what the operator intended. Route metric comparison is generally relevant among routes of comparable prefix specificity; it does not make a broad `/8` override a more specific `/24` merely because someone prefers the VPN.

Routing chooses a suitable outbound interface and next hop. On an IPv4 Ethernet link, ARP can resolve the local next hop's IP address to its link-layer address so a frame can be sent. ARP does not discover the remote server's MAC address across the internet. In IPv6, Neighbor Discovery fills the corresponding local-link role. Overlapping address spaces are a common reason an apparently connected VPN does not reach its intended internal resources.

### A05 — Why one write becomes three reads

TCP provides an ordered, reliable **byte stream**, not a sequence of application messages. Write calls and read events are not guaranteed to have a one-to-one relationship. Segmentation, buffering, scheduling, and coalescing can split one logical message or combine several; this is normal behavior.

Define framing at the application layer: for example, a length-prefixed payload, a newline-delimited format with correct escaping, or an established protocol such as HTTP. Accumulate bytes until a complete frame is available, enforce a maximum permitted message size, and handle partial frames and multiple frames in one buffer. Respect backpressure when the receiver cannot keep pace. Trying to `JSON.parse` each individual `data` event is a classic bug masquerading as a network failure.

### A06 — The payment response disappeared

A timeout means the client did not observe completion within its deadline; the server or supplier may have committed the reservation and merely lost or delayed the response. Blindly retrying a creation request can generate two reservations or charges. `GET` is intended to be safe, while `PUT` and `DELETE` are defined as idempotent operations in HTTP semantics; ordinary `POST` is not automatically idempotent. None of these method labels guarantees that an incorrectly implemented business workflow is safe.

For reservation creation, accept a stable client-generated idempotency key, atomically associate that key and request identity with the operation, and return the same durable outcome for equivalent retries. Reconcile ambiguous supplier results and avoid treating a failed HTTP exchange as proof that a transaction did not occur. The important property is business-level idempotency backed by appropriate storage and semantics, not simply choosing a different verb.

### A07 — A private service cannot call its supplier

Successful outbound traffic requires an appropriate destination, a route toward that destination, a permitted outbound and return path, and a way for the public service to return traffic to the source. A private IPv4 instance normally needs a default or specific route through a NAT gateway or an approved egress proxy; in common AWS designs the NAT gateway uses a public subnet and an internet gateway for public internet egress. Security group rules, network ACLs and upstream controls can independently deny packets. A database being reachable in the VPC proves none of these internet requirements.

Check DNS resolution, the effective subnet route table, gateway health, network policies, security rules, and observed connections from inside the workload. The supplier may allowlist the translated public egress IP; a working NAT path with an unapproved IP can still fail at the supplier. Don't confuse NAT with a firewall, or a “public subnet” designation with every instance automatically having a usable public address.

### A08 — Chrome succeeds; Node.js distrusts the endpoint

TLS aims to provide confidentiality, message integrity, and authenticated peer identity when validation is performed correctly. The client must verify that the presented certificate is valid for the intended hostname and chains to a trusted authority, subject to the certificate's constraints and validity period. Merely encrypting traffic without authenticating the peer is not sufficient against a man-in-the-middle attacker.

The browser and Node.js may have different trust stores or intermediate-certificate retrieval behavior. The server may omit an intermediate certificate, present the wrong certificate due to SNI or hostname configuration, or rely on a private root trusted only by one client. Capture the actual hostname, certificate chain, client/runtime versions, trust roots, and TLS error; compare the same endpoint with diagnostic tooling. Fix the server chain or legitimate trust configuration. `rejectUnauthorized: false` hides the defect by removing a core security guarantee.

### A09 — HTTP/1.1, HTTP/2, HTTP/3

HTTP/1.1 commonly uses persistent TCP connections, but efficient parallelism often requires multiple connections because practical pipelining is limited. HTTP/2 multiplexes framed request/response streams on one TCP connection and compresses headers. It removes HTTP-layer head-of-line blocking among requests, but loss of a TCP segment can delay delivery of data on other streams sharing that TCP connection.

HTTP/3 preserves modern HTTP semantics while running over QUIC on UDP. QUIC supplies encryption and reliable, independently ordered streams, so a lost packet carrying one stream's data need not block delivery of already received data on another stream. Packet loss can still reduce throughput through congestion control, and UDP connectivity, server implementation, middleboxes, connection setup, and traffic patterns all affect performance. Clients must also discover and successfully negotiate HTTP/3, often falling back to HTTP/2. No version wins every workload.

### A10 — The response came from somewhere else

An edge cache can serve a stored HTTP response without contacting the origin, including a dangerously misconfigured cache entry containing private customer data. The critical questions are: which component produced this `200`, under what cache key was it stored, and what rules allowed a shared intermediary to store or reuse it? A URL-only cache key is unsafe when authorization, cookie state, or another request dimension changes the representation.

Correlate edge request logs and cache status, inspect cache rules and effective headers, and trace whether the origin ever produced and labeled that representation. Contain exposure by disabling the unsafe caching rule and purging affected objects while investigating scope. Authenticated customer data should generally not be stored in shared caches; `Cache-Control: private` prohibits shared-cache storage, while `no-store` asks caches not to store it at all. Also audit authorization: correct cache behavior does not compensate for a backend that returns the wrong customer's booking.

### A11 — Streaming that arrives all at once

An application can flush progress chunks while a reverse proxy, CDN, compression middleware, framework adapter, or browser-facing intermediary buffers them before forwarding. The symptom strongly suggests buffering or output handling along the path, but it is not a root-cause proof. Inspect bytes arriving at the origin-facing and client-facing sides, proxy buffering settings, compression, response framing, idle timeouts, and whether the client actually processes streaming events incrementally.

For a one-way progress feed, server-sent events are often a simpler fit: ordinary HTTP, text/event-stream framing, and browser-friendly automatic reconnection. WebSockets suit ongoing bidirectional interaction but bring different connection lifecycle and operational considerations. Neither magically supplies durable history or infinite buffers. Include heartbeats where necessary, support resumption or status snapshots if gaps matter, and handle slow consumers and backpressure.

### A12 — Who can you trust behind a load balancer?

TLS from the browser terminates at the load balancer; the connection from the load balancer to the application is another transport and possibly another TLS session. The external padlock does not prove the internal hop is encrypted or authenticated. Whether to re-encrypt that hop depends on network topology, threat model, compliance requirements, and operational design.

The application often needs the original scheme, host, and client IP for redirects, secure cookies, audit logs, or policy. Trusted intermediaries can transmit this information using forwarding headers, but a public client can also supply headers with the same names. The application must define which proxy hops are trusted and ensure that untrusted incoming values are stripped, replaced, or interpreted through an explicitly configured trusted-proxy chain. Otherwise an attacker may spoof client identity or make security-sensitive logic believe a request used HTTPS when it did not.

### A13 — The first request after idle fails

A connection pool may select a TCP connection that the server, proxy, firewall, or load balancer closed after its idle timeout. The client believes the socket is reusable until its next I/O encounters a reset; opening a fresh connection then succeeds. Compare outcomes with pooling enabled and disabled, measure idle durations, inspect socket close events, proxy idle timeouts, and connection reuse metrics. Keep-alive policies at different layers can have different meanings and defaults.

Recycling idle connections earlier, validating pool health, or retrying on a new connection can help. But an HTTP client losing the response does not know whether a state-changing request was processed. Automatically replaying a non-idempotent booking operation may duplicate it. Retry only when semantics and application-level idempotency make it safe, within an overall deadline.

### A14 — An edge 504 with no application trace

A `504` typically reports that a gateway or proxy did not receive an adequate response from an upstream within its deadline. It does not establish that Node.js generated the error or that the database was slow. First determine which hop produced the 504 and whether the request was forwarded, which upstream target was selected, and whether a connection was actually established.

Correlate edge and load-balancer access logs, target health, upstream connection and response timings, network route/security policy, and distributed trace IDs. A connection timeout before the application receives anything points toward reachability or accept capacity; a healthy connection with a long wait and a matching server trace points toward application processing. A missing app trace is evidence only if logging coverage is reliable. Increasing a database timeout before identifying the boundary risks making the incident worse while explaining nothing.

### A15 — Large requests vanish in a VPN

One network hypothesis is Path MTU Discovery failure: encapsulation adds overhead, a packet exceeds some link's usable MTU, and necessary ICMP feedback is blocked, producing retransmissions or black-hole behavior for larger transfers. But size-dependent failures also arise from reverse-proxy body limits, request buffering, application size validation, stream timeouts, and HTTP framing problems.

Find the smallest payload that reproduces the issue and compare the same request on and off the VPN. Inspect whether the proxy or application receives bytes, whether a clear HTTP `413` or similar response appears, whether packet traces show retransmissions, and whether ICMP or path-MTU signals are present. Controlled packet-size tests can distinguish network path effects from body-size policy. The goal is not to guess “MTU” faster than the team; it is to produce evidence that eliminates other explanations.

### A16 — The IPv6-shaped outage

Clients may receive both A (IPv4) and AAAA (IPv6) answers and choose different address families or fallback behavior. The IPv6 endpoint may lack a working listener, routing path, firewall allowance, correct TLS virtual-host configuration, or required Neighbor Discovery and ICMPv6 behavior. A correct IPv4 connection says little about the IPv6 path.

Compare DNS results and actual destination addresses on affected clients, then test TCP/TLS explicitly over IPv4 and IPv6. Check address binding, load-balancer listeners, security rules, return routes, and the behavior of dual-stack connection selection, including Happy Eyeballs implementations. Some clients can hide IPv6 defects through quick fallback; others expose them as long delays. A dual-stack service has two network paths to verify, not one.

### A17 — Extension: `curl` succeeds, browser JavaScript fails

CORS is an additional **browser security policy**, not a transport protocol. `curl` can connect, complete TLS, and read the response even when a browser refuses to expose that response to JavaScript from another origin. An origin consists of scheme, hostname, and port. The browser evaluates CORS response headers to decide whether cross-origin script access is allowed. This is not proof of broken DNS or TCP.

For certain cross-origin requests, such as those using non-safelisted headers or methods, the browser first sends an `OPTIONS` preflight to ask whether the actual request is permitted. The server must correctly respond to the relevant origin, method, and headers, and credentialed requests require special care: a wildcard `Access-Control-Allow-Origin` cannot be used with credentialed CORS access. Inspect browser network details and both the preflight and actual response. CORS is not authentication and does not replace server-side authorization.

### A18 — Extension: The same service fails only in Kubernetes

DNS resolution proves the Pod obtained a name answer; it does not prove that packets can reach the remote service, that TCP connects, or that TLS and HTTP succeed. Failure of ICMP echo (`ping`) is also inconclusive: firewalls and remote services commonly block it while permitting HTTPS. Both colleagues are over-interpreting one narrow observation.

From within the actual Pod or an equivalently configured diagnostic container, test DNS addresses, a TCP connection to the intended port, TLS validation, and the HTTP response. Compare with the laptop path. Inspect Kubernetes NetworkPolicy egress, service-mesh sidecars or proxies, node/VPC routing, NAT gateway and public egress IP, security groups, and remote IP allowlists. A Pod may have a completely different source address and policy environment from the developer laptop. Locate the first failing boundary before changing application code or cluster-wide permissions.
