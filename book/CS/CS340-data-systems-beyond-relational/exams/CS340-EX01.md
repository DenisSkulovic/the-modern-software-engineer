# CS340 — Course Examination EX01: The Database Is Not the Architecture

**Course:** Data Systems Beyond Relational Databases · **Coverage:** CS340-L01–L07, with practical MongoDB emphasis  
**Audience:** Experienced full-stack/backend engineer · **Approach:** Reason first; solutions in Part II.  

This is not a contest to name databases or memorize MongoDB operators. Think in **access patterns, correctness boundaries, and operational cost**. Assume a product company with real production data, not a laboratory benchmark.

# Part I — Questions

## Round A — Model the thing you're building

### Q01 — The proposal for five databases
A startup stores bookings in PostgreSQL. A colleague wants MongoDB for hotel catalogues, Redis for speed, Elasticsearch for search, a graph database for recommendations, and an analytics warehouse—immediately. How would you evaluate the proposal?

### Q02 — One enormous customer document
A MongoDB schema embeds every purchase, note, payment event, and activity log for a customer in one document. It initially works beautifully. Over time, updates get slower and documents become unwieldy. How would you redesign the boundary?

### Q03 — The customer changes their address
A reservation document copied a customer's shipping/billing details at checkout. The customer later edits their profile and complains that the old invoice didn't change. Is that a bug or intentional design? How do you decide?

### Q04 — Two requests change the same balance
A MongoDB application reads a document's balance, calculates a new value in JavaScript, and writes it back. Two concurrent calls occasionally lose one update. What would you change and why?

## Round B — Query performance in the real world

### Q05 — A tiny page takes minutes
A collection contains tens of millions of findings. An aggregation joins in related data, sorts a huge intermediate result, and only then applies a limit of 20. Why can this be dramatically slower than the output size suggests? How would you investigate?

### Q06 — The index exists but nothing improved
A high-volume query filters by tenant and scan, sorts by severity, and returns a page of findings. Someone adds an index on severity alone and declares the performance issue solved. How would you test that claim and consider a better index?

### Q07 — Reaching the last page
An admin wants the last twenty records of a huge filtered result set using `skip` and `limit`. The team says the query only returns twenty documents, so it should be cheap. Evaluate this reasoning and propose alternatives.

### Q08 — The wrong room passes the filter
A hotel document embeds an array of rooms. A query seeks a room that is both `type: "suite"` and `available: true`, but it also matches hotels where one room is a suite and a different room is available. Why might this happen, and what would you inspect?

### Q09 — A field copied from another collection
To avoid an expensive repeated lookup, a team stores a frequently needed derived attribute on each finding. The dashboard becomes much faster. What new responsibilities did this optimization create, and when would you accept it?

## Round C — Data systems under failure and growth

### Q10 — The write succeeded, then seemed to disappear
An application received acknowledgment for a database write, the primary failed shortly afterward, and the new primary does not show the record. How could this happen? What product guarantees would you clarify?

### Q11 — One tenant overwhelms one shard
A large multi-tenant collection is sharded, but one large tenant still dominates latency despite plenty of total cluster capacity. Why might adding shards fail to fix the issue? What makes a useful distribution key?

### Q12 — Search shows yesterday's version
The source database is correct, but the search index occasionally displays stale names and sometimes even reverts a newer update. What architecture might produce this, and how would you make synchronization safer?

### Q13 — Redis is fast until it isn't
A hot-cache outage causes PostgreSQL to collapse under traffic. How would you improve the system without treating Redis as the unquestioned source of truth?

### Q14 — The analytics query that slows checkout
Product management wants an expensive daily report over transaction data. Running it directly on the primary database degrades customer bookings. What realistic alternatives exist, and how would you choose among them?

# Part II — Model Answers and Reasoning

### A01 — The proposal for five databases
Start with what must be correct, the actual queries, scale, team expertise, and operational tolerance. PostgreSQL may already serve catalogue metadata and moderate search well enough. Add Redis if measurement shows repeated expensive work worth caching; dedicated search if ranking/full-text requirements justify it; analytics storage when reporting hurts operational workloads. MongoDB can be a good fit for document-shaped aggregates but isn't automatically superior for catalogues. Every additional data system creates backups, security, monitoring, migrations, synchronization, and failure paths. Demand a specific unmet requirement for each choice, not a technology shopping list. Specialized stores should usually be derived projections of an authoritative source unless their contract explicitly makes them authoritative.

### A02 — One enormous customer document
Embedding works for bounded information read and updated together. Unbounded purchases and logs grow indefinitely, create document growth/update costs, and make pagination and independent retention awkward. Split long-lived entities from append-only events into separate collections keyed by customer, with indexes supporting common reads. Keep a compact customer summary or recent-items subset if the UI needs it. Preserve atomicity for operations that truly belong together; cross-document workflows may need transactions or explicit consistency. Choose boundaries from workload and business invariants, not because MongoDB demands embedding everything. Consider MongoDB document size limits and array-related indexing costs in the design.

### A03 — The customer changes their address
An invoice usually records what was agreed at the time of the transaction; changing it retrospectively would often be incorrect. A current profile and a historical transaction snapshot have different semantics. It is sensible to copy transaction-time name/address/price into the reservation or invoice while retaining a reference to the current customer. Decide which fields are immutable, which may be corrected through audited adjustments, and applicable legal/business requirements. Duplication is not inherently a bug when different copies represent different points in time. A read of the customer's present profile should not silently rewrite historical truth.

### A04 — Two requests change the same balance
Read–calculate–overwrite is vulnerable to lost updates. Use an atomic database-side update when the invariant is local to one document—for example a conditional `$inc` guarded against unacceptable balances—and check whether the update matched. For more complex business transitions, use an optimistic version check or a transaction with a clear conflict/retry policy. A single-document update is atomic in MongoDB, but a sequence of separate reads and writes isn't automatically atomic. Also distinguish a numeric account balance from an accounting ledger: for financial correctness, immutable entries and reconciled totals may be preferable to treating a mutable number as the only truth.

### A05 — A tiny page takes minutes
The database must perform all stages required before producing twenty results. A `$lookup` can multiply work across a huge collection, a blocking `$sort` can consume memory or spill, and a late `$limit` doesn't retroactively make earlier work cheap. Start with the full pipeline, stage ordering, representative filters, and `explain` output (documents/keys examined, execution time, sort/spill behavior). Push selective filters earlier when semantics permit, use aligned indexes, avoid unnecessary join fan-out, and consider precomputing stable derived data. Moving `$limit` earlier is only valid if it preserves the intended result order and filtering—don't optimize away correctness.

### A06 — The index exists but nothing improved
An index on severity may scan values across all tenants and scans, then filter most of them away. Examine representative `explain` plans for the exact query shape and distributions. A compound index beginning with equality filters such as tenant and scan, followed by sort-related fields, may let MongoDB find and order relevant documents with less work. The precise order depends on range predicates, equality constraints, sort directions, and cardinality; it is not a universal slogan. Compare keys/documents examined to results returned, sort stages, and memory. Also consider write amplification and index size on a large collection. The best index is for a workload, not a field name.

### A07 — Reaching the last page
A deep `skip` often requires walking and discarding many qualifying records first, even if only twenty are returned. If arbitrary numbered pages are unnecessary, keyset pagination with a stable compound sort key and an anchored cursor is usually more scalable. For true backward navigation, use the opposite sort condition and reverse output appropriately. If the product requires exact total page counts and direct jumps, discuss the cost, approximate counts, precomputed positions, or constrained search windows. An index helps filter/order but doesn't make deep skipping constant-time. The real problem might be the product's navigation requirement rather than the database's speed.

### A08 — The wrong room passes the filter
With separate predicates on an array of objects, MongoDB may satisfy them using different array elements. An `$elemMatch` condition expresses that both constraints must apply to the same element. Confirm the actual document shape, query, and index strategy; distinguish a single room matching all conditions from a hotel containing some suitable type and some available room. This is not just syntax trivia: wrong array semantics can return invalid business results. If rooms need independent reservations, writes, or pagination, that may also argue for a separate collection rather than ever-growing nested arrays.

### A09 — A field copied from another collection
Denormalization trades extra write/synchronization work for cheaper reads. You now must specify who owns the attribute, when and how copies update, whether eventual staleness is acceptable, how to backfill old records, and what to do when events arrive out of order. Use versions or timestamps carefully to reject older updates replacing newer facts where appropriate, and monitor divergence. This optimization is justified when expensive repeated joins or aggregations dominate a real workload and the derived field has clear consistency semantics. The real cost of storing a field isn't only its bytes; it's keeping its meaning correct over time.

### A10 — The write succeeded, then seemed to disappear
Acknowledgment by one node need not imply the write was durably replicated to a surviving majority. An asynchronously replicated secondary might be elected before receiving the latest change. In MongoDB, appropriate write concern (such as majority for the relevant guarantee) changes what an acknowledgment means, although other failure semantics and timeouts still matter. Clarify whether losing an acknowledged reservation is acceptable, the durability/latency trade-off, and what the application does when an acknowledgment is uncertain. Distinguish replication from backups. A write timeout isn't proof that a write was rolled back; reconciliation may still be required.

### A11 — One tenant overwhelms one shard
Distribution only helps when the shard key spreads the hot workload and queries can target relevant shards. A key based solely on tenant might put all of a huge tenant's hot data or traffic onto a limited portion of the cluster. Examine query routing, cardinality, skew, monotonically increasing keys, and locality of updates. A composite or hashed strategy may spread load, but can increase scatter-gather queries or complicate tenant-scoped access. Adding machines without changing the hotspot's placement doesn't remove the bottleneck. Ask first whether sharding is necessary or whether indexing, partitioned workloads, or isolated big tenants are simpler.

### A12 — Search shows yesterday's version
Search is often a derived index updated asynchronously from an authoritative database. Events can be delayed, dropped, retried, or processed out of order, so a stale event may overwrite a newer projection. Provide a reliable source of changes (outbox/change data capture), replayable ingestion, idempotent indexing, record versions to reject stale updates, and monitoring of lag. Build a backfill and reconciliation procedure. Critical writes should still be validated against the source of truth; search results can be stale by design. Introducing a search engine adds a synchronization product, not merely a new query endpoint.

### A13 — Redis is fast until it isn't
A cache creates a dependency-shaped load pattern: normal traffic hides origin capacity requirements until widespread misses suddenly flood the database. Cap fallback concurrency, protect the database with rate limits/load shedding, and choose whether bounded stale responses are allowed. Prewarm or stagger hot keys, use request coalescing, and monitor hit rates and origin load. Redis should be treated according to its contract; if it is only a cache, it should not be the sole authority for financial or transactional facts. Plan for cache cold starts and outages in capacity testing, not only steady-state benchmark numbers.

### A14 — The analytics query that slows checkout
Separate operational and analytical workloads according to freshness, scale, and cost requirements. Options include optimized aggregates on the primary during off-peak windows, a read replica (with replication lag and resource caveats), incremental summary tables, a change-stream/event pipeline, or an analytical warehouse for richer workloads. Ask whether the report must be exact and immediate, how far behind it may be, and whether it can be recomputed. Avoid duplicating all production data into a second system without ownership and reconciliation plans. The correct architecture protects booking latency while delivering the business reporting requirement at an acceptable cost.

## Closing perspective

Choose storage based on **truth, query patterns, and failure behavior**, not fashion. If a MongoDB query returns twenty records after examining twenty million, twenty is not its cost.
