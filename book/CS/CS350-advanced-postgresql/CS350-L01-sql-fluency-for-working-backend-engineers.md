# CS350 — Advanced PostgreSQL Engineering
## Lecture 01: SQL Fluency for Working Backend Engineers

*Your interviewer asks for the five customers generating the most revenue. You know what a database is, you know what an index does, and you've debugged production systems. But can you actually write the query?*

---

# Part I — Intuition

## 1. The Interview That Exposed a Different Kind of Weakness

Imagine interviewing for a senior full-stack position at a European product company.

The interviewer describes a familiar system: a hotel-booking platform with customers, reservations, payments, and refunds.

They give you a PostgreSQL database containing six tables.

Then they ask:

"Find the five customers generating the greatest net revenue from confirmed bookings over the last ninety days. Account for partial refunds, exclude cancelled bookings, and include customers with no qualifying activity when calculating the ranking."

You understand the business.

You've worked with backend APIs, databases, asynchronous services, and production incidents. You've seen SQL through ORMs, read queries generated by frameworks, and perhaps asked an AI assistant to construct complicated reports.

You know that joins connect tables, `GROUP BY` aggregates rows, and `ORDER BY` sorts results.

Yet staring at the blank SQL editor feels different.

Where should you begin?

Do you join customers to bookings, then payments, then refunds?

What happens if one booking has two payments?

What if a payment has several partial refunds?

Does a cancelled booking contribute revenue?

Should customers without bookings disappear?

And how do you know whether your answer is correct?

This is the difference between **recognizing SQL concepts and composing a correct query independently**.

The objective of this course is to eliminate that gap.

## 2. SQL Is a Language for Describing Sets of Facts

Imagine a database containing six customers and several bookings.

Alice has two recent confirmed bookings.

Bob has two.

Cara has one.

Dan has one old booking.

Erin has two recent confirmed bookings.

Fay has never booked anything.

A conventional programming approach might load the customers into memory, loop over their bookings, look up payments, subtract refunds, and sort the resulting array.

SQL lets us describe the desired result through relational operations.

We decide which rows qualify, how tables relate, which groups we need, which calculations belong to those groups, and how to order the final result.

The database then chooses an execution strategy.

This is the declarative model discussed in CS330-L02.

But today we're not primarily studying the database optimizer.

We're learning to express the problem correctly.

The first step is to stop thinking of a SQL query as a clever sequence of keywords.

Think of it as a transformation from one well-defined set of rows into another.

## 3. The Most Important Question: What Does One Row Represent?

Suppose our database contains three tables:

A booking table with one row per reservation.

A payment table with one row per payment attempt.

A refund table with one row per refund.

A customer may have many bookings.

A booking may have several payments.

A payment may have several refunds.

These relationships matter because joining tables changes the number of rows.

Imagine booking number 103 belongs to Bob.

It has two captured payments, each worth €150.

One of those payments has a successful €25 refund.

The correct net revenue is €275.

But if we join booking line items, payments, and refunds without accounting for their different cardinalities, we may duplicate amounts.

The query can execute successfully and produce a plausible-looking result that is mathematically wrong.

This is one of the most dangerous SQL mistakes.

No exception occurs.

The database does exactly what you asked.

You asked the wrong question.

The word *grain* describes what one row represents.

A booking-level report requires booking-level facts.

A customer-level report requires customer-level facts.

If we combine facts at incompatible grains without care, their values can multiply.

**Before writing a join, know the grain of both sides. Before aggregating, know the grain of the result.**

## 4. Filtering and Aggregating Answer Different Questions

Suppose the interviewer asks for confirmed bookings made during the last ninety days.

The first decision is which bookings qualify.

That's a row-level filtering problem.

SQL uses `WHERE` to decide which source rows enter subsequent operations.

After finding qualifying bookings, we may group them by customer.

That's an aggregation problem.

SQL uses `GROUP BY` to establish those groups.

Then perhaps we want only customers with at least two confirmed bookings.

That's a condition on the aggregated result.

SQL uses `HAVING` for that purpose.

These distinctions are much easier to remember when tied to the actual question.

**WHERE selects source rows. GROUP BY establishes groups. HAVING filters groups.**

For example, a booking can be excluded because it is cancelled before any revenue calculation occurs.

A customer can then be excluded because their aggregate revenue does not meet a reporting threshold.

Different stages, different responsibilities.

### Visual anchor 2 — The logical data transformation

```text id="3c7ivz"
Source tables
     |
     v
Join relevant relationships
     |
     v
Filter qualifying rows
     |
     v
Group by customer
     |
     v
Calculate aggregates
     |
     v

     |
     v

     |
     v

```

This is a conceptual order for interpreting a typical grouped query, not a promise about the database's physical execution plan.

PostgreSQL may rearrange operations while preserving the query's semantics.

That distinction becomes important in the next lecture.

## 5. Why Missing Data Is Not the Same as Zero

Return to Fay.

She has never made a booking.

The report should still include her, with zero bookings and zero revenue.

If we start from bookings and join customers, Fay never appears because there's no booking row associated with her.

If we start from customers and use an inner join, Fay disappears for the same reason.

A left join allows us to retain customers even when matching booking data doesn't exist.

But a subtle trap remains.

Suppose we left join bookings and then write a `WHERE` condition requiring the booking to be confirmed.

For Fay, the booking columns are null.

The condition fails, and Fay disappears.

We accidentally turned our outer join into something that behaves like an inner join for this condition.

A common correction is to filter the booking rows before joining, or place the qualification inside the join condition.

Now Fay remains in the result.

But we must also count correctly.

`COUNT(*)` counts rows in the result group, including the preserved customer row without a matching booking.

`COUNT(booking_id)` counts non-null booking IDs.

For Fay, the second expression correctly produces zero.

### Visual anchor 3 — Preserving customers without bookings

SQL `NULL` is not zero.

It means a value is missing or unknown in the relevant context.

And operations involving null do not always behave like ordinary arithmetic or equality comparisons.

Learning these details is not pedantry.

It's what prevents reports from silently excluding part of the business.

## 6. Break a Hard Query into Named Intermediate Results

Our original revenue question involves customers, qualifying bookings, captured payments, and successful refunds.

Trying to express the entire calculation in one enormous join can become difficult to reason about.

A more reliable approach is to build the result in stages.

First, identify the confirmed bookings in the reporting window.

Second, calculate captured payments per booking.

Third, calculate successful refunds per booking.

Fourth, combine those booking-level amounts to calculate net revenue.

Finally, aggregate booking-level net revenue per customer.

SQL provides Common Table Expressions, usually called CTEs, to express these intermediate relations.

A CTE begins with `WITH` and gives a name to a subquery.

Think of it as naming an intermediate result so that the rest of the query can reason about it.

A CTE is not necessarily a physical temporary table. PostgreSQL may inline or materialize it depending on the query and optimizer rules.

But the human readability advantage is immediate.

You can inspect each stage independently.

**A complicated query becomes manageable when every intermediate relation has a clear grain and responsibility.**

## 7. SQL Is Also About Proving the Answer

Suppose you run your query and it returns:

Alice: €450.

Bob: €275.

Erin: €120.

Cara: €80.

Dan: €0.

Those numbers look reasonable.

But why should you trust them?

Perhaps Alice's €450 is correct.

Perhaps her payments were duplicated by a join and then accidentally reduced by another duplicate.

Perhaps pending refunds were subtracted.

Perhaps a cancelled booking slipped into the calculation.

A successful query execution proves that the database accepted the SQL.

It does not prove that the business logic is correct.

A strong engineer validates intermediate results, boundary cases, and expected totals.

For example:

Does Bob's booking with two payments produce €300 before refunds?

Does its successful €25 refund reduce the net amount to €275?

Does Erin's failed payment contribute zero captured revenue?

Does Cara's cancelled booking contribute nothing?

Does Fay appear with zero activity?

We need to reason about the result before measuring the query's performance.

Optimizing an incorrect report simply produces incorrect answers faster.

## 8. A Tiny Comprehension Check

Consider a customer with one confirmed booking.

The booking has two captured payments: €100 and €200.

One payment has two successful refunds: €20 and €30.

What is the net captured revenue?

€250.

Now suppose we join the payment rows directly to the refund rows and simply sum payment amounts.

Could that produce an incorrect result?

Yes.

The payment associated with two refunds may appear twice in the joined result.

That changes the apparent total.

The safe mental model is to aggregate each financial relationship at its appropriate grain, then combine the resulting facts.

This is the central lesson of our first course chapter.

SQL fluency is not knowing dozens of functions.

It is knowing how to express a business question without accidentally changing what the data means.

*The intuition pass ends here.*

# Part II — Deep Dive

## 9. Translate Business Language into a Query Contract

Before writing SQL, turn the request into a precise contract.

Our interviewer says:

"Show the five customers with the greatest net revenue from recent confirmed bookings."

Several details need definitions.

What does recent mean?

We'll use a fixed ninety-day window ending at midnight UTC on October 29, 2026, so the exercises produce reproducible results.

What does confirmed mean?

Only bookings with `status = 'confirmed'` qualify.

What does revenue mean?

For this exercise, it means captured payment amounts less successful refunds associated with qualifying bookings.

Pending and failed payments don't count.

Pending refunds don't count.

The report covers bookings created in the specified window, using the currently recorded payment and refund outcomes in the fixture. It is not a complete historical accounting ledger as of an arbitrary point in time.

What happens to customers without qualifying bookings?

They remain in the result with zero revenue.

What happens when revenue is tied?

Order by customer ID to make the result deterministic.

Now we have a query specification.

Without these definitions, two engineers can write different SQL statements that both appear reasonable but answer different business questions.

### 9.1 Grain and cardinality

The output needs one row per customer.

The intermediate revenue calculation should produce one row per booking.

The captured-payment aggregate should produce one row per booking.

The successful-refund aggregate should also produce one row per booking.

Once those grains are established, the joins become much easier to reason about.

## 10. Joins Are Relationships with Multiplicity

Let's examine the basic join types from an application developer's perspective.

An inner join returns combinations of rows where the join condition matches.

A left join preserves every row from the left relation, with null values for columns from the right when no match exists.

A cross join produces every combination of rows from two relations.

A full outer join preserves unmatched rows from both sides.

The important practical issue is often cardinality.

Suppose a customer has three bookings.

Joining customers to bookings produces three rows for that customer.

If each booking has two line items, joining the booking items may produce six rows.

If each booking also has two payments, combining both child tables can produce even more rows.

That may be correct if the query intentionally needs every combination.

But it is dangerous when summing money.

### 10.1 The multiplication trap

Imagine a booking with two line items and two payments.

Joining booking items and payments on the booking ID produces four combinations.

Summing the payment amounts across those combinations can count each payment twice.

The usual fix is not `DISTINCT` sprinkled over the final result.

`DISTINCT` removes duplicate result rows according to selected values. It does not generally repair duplicated financial facts.

The safer design is to aggregate payments by booking before joining them to other booking-level facts.

### 10.2 Check cardinality deliberately

When a query returns unexpectedly large totals, inspect intermediate row counts.

Count rows before and after each join.

Group by the entity identifier and examine how many rows appear per entity.

Use a small sample booking whose expected result can be calculated manually.

Do not assume that a foreign key implies a one-to-one relationship.

A foreign key tells you about referential integrity, not necessarily uniqueness on the referencing side.

## 11. `GROUP BY`, `HAVING`, and Conditional Aggregates

Grouping transforms a collection of source rows into groups identified by selected expressions.

For example, grouping bookings by customer ID allows us to calculate booking counts.

`COUNT(*)` counts source rows in each group.

`COUNT(booking_id)` counts rows whose booking ID is not null.

`SUM(amount)` adds non-null amount values.

`AVG(amount)` calculates a mean over non-null values.

An important detail: most aggregates return null when there are no input values. `COUNT` returns zero.

That's why `COALESCE` frequently appears in reporting queries.

It replaces a null expression with a specified fallback value.

### 11.1 Conditional aggregation

Suppose we want to count confirmed and cancelled bookings in one query.

PostgreSQL supports the `FILTER` clause on aggregates.

For example, an expression equivalent to counting only confirmed bookings can use `COUNT(*) FILTER (WHERE status = 'confirmed')`.

This is often cleaner than constructing a separate query for every status.

Conditional sums are useful too.

But remember that conditions placed in the aggregate filter affect that aggregate, while a general `WHERE` condition affects which source rows remain available to all aggregates.

### 11.2 `WHERE` versus `HAVING`

Suppose the requirement is customers with at least two confirmed bookings.

Filter confirmed bookings before grouping.

Then use `HAVING` to select groups whose count is at least two.

For queries preserving customers with zero activity, consider whether the filtering belongs inside the join or in a prefiltered relation.

A poorly placed `WHERE` condition can eliminate the rows you intended to preserve.

## 12. CTEs: Decompose Before You Optimize

A Common Table Expression gives an intermediate relation a name.

Imagine the following conceptual steps:

`qualifying_bookings` contains one row per confirmed booking in the reporting window.

`captured_by_booking` contains one row per booking with the sum of captured payment amounts.

`refunded_by_booking` contains one row per booking with the sum of successful refunds.

`net_by_booking` combines those amounts.

The final query joins customers to `net_by_booking`, groups by customer, sorts, and returns five rows.

This structure makes the financial logic auditable.

You can run each CTE's underlying query independently and check its results.

### 12.1 CTEs are not always optimization fences

Older PostgreSQL versions commonly materialized CTEs, which affected optimization opportunities.

Modern PostgreSQL can fold suitable non-recursive, side-effect-free CTEs into the surrounding query.

Whether a CTE is materialized depends on several conditions, and developers can sometimes influence the behavior with `MATERIALIZED` or `NOT MATERIALIZED`.

For this lecture, use CTEs primarily to express correctness.

In CS350-L02, we'll investigate how the planner actually executes them.

Readable SQL and efficient SQL are not enemies.

But readability does not automatically establish performance.

## 13. Window Functions: Keep the Rows, Add Context

Ordinary aggregation often collapses multiple source rows into one group result.

Window functions behave differently.

They calculate values across related rows while preserving the individual rows.

Suppose we want each customer's bookings ordered from newest to oldest, with a sequence number.

A window function such as `ROW_NUMBER()` can assign a number to each booking within its customer's partition.

Conceptually:

`ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY booked_at DESC, booking_id DESC)`

The partition divides rows by customer.

The ordering determines which booking comes first.

The tie-breaker makes the sequence deterministic when multiple bookings share the same timestamp.

### 13.1 Ranking isn't always row numbering

`ROW_NUMBER()` assigns a distinct sequence number even when sort values tie.

`RANK()` gives tied rows the same rank but leaves gaps.

`DENSE_RANK()` gives tied rows the same rank without gaps.

These distinctions matter when the business asks for the top three ranks rather than precisely three rows.

### 13.2 Running totals

A window aggregate can calculate a running total over a customer's chronological bookings.

The frame determines which rows participate in each calculation.

For a row-by-row running total, an explicit frame such as `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` makes the intention clear.

Do not assume every ordered window aggregate uses precisely the row frame you have in mind.

Default frames can include peers in ways that surprise developers.

### 13.3 Window functions do not replace grouping

If you need one row per customer, ordinary aggregation may be the right tool.

If you need one row per booking plus its position within the customer's history, a window function is useful.

The choice follows the grain of the desired result.

## 14. `EXISTS`: Ask Whether a Relationship Exists

Sometimes the business question isn't about retrieving related rows.

It's about whether any qualifying related row exists.

For example:

"Find customers who have never made a booking."

An anti-join can solve this.

Another natural expression is `NOT EXISTS`.

A correlated subquery checks whether at least one booking references the customer.

If none exists, the customer qualifies.

`EXISTS` can be useful because it expresses the actual business question without requiring the outer query to deal with duplicated matching rows.

### 14.1 Why `NOT IN` can be dangerous

A `NOT IN` subquery containing null values can produce unexpected results because SQL uses three-valued logic.

The comparison may evaluate to unknown rather than true.

`NOT EXISTS` is often a safer and clearer way to express the absence of related rows.

This isn't a universal ban on `NOT IN`.

It's a reminder to understand null semantics before using it.

## 15. Pagination: Sorting Is Part of the Contract

Suppose our admin interface lists confirmed bookings, newest first.

A query uses `ORDER BY booked_at DESC LIMIT 20`.

What if two bookings have exactly the same timestamp?

Their relative order is not fully specified.

For stable pagination, include a unique tie-breaker, such as booking ID.

Now the ordering is deterministic.

### 15.1 Offset pagination

With offset pagination, page ten might use `LIMIT 20 OFFSET 180`.

This is simple and useful for modest datasets.

But the database still has to account for skipped rows.

Deep offsets can become expensive.

Additionally, if rows are inserted or deleted between page requests, the user may see duplicates or miss entries.

### 15.2 Keyset pagination

Keyset pagination uses the values from the last returned row.

For a descending order by booking timestamp and booking ID, the next page can request rows whose `(booked_at, booking_id)` tuple is smaller than the previous page's final tuple.

This avoids repeatedly skipping large numbers of earlier rows.

It also gives the pagination operation a clearer relationship to an ordering cursor.

But it doesn't automatically create a consistent snapshot across multiple requests.

If the underlying data changes, pagination semantics still require thought.

And it is less convenient for arbitrary jumps to page 500.

We will investigate execution costs and index support in the next lecture.

## 16. Updates Are Not Merely SELECT Statements with Different Verbs

SQL fluency includes modifying data safely.

A backend engineer should be comfortable with `INSERT`, `UPDATE`, and `DELETE`.

But those operations have business consequences.

Suppose a booking is pending and the customer cancels it.

A conditional update can change its status only if the current status remains pending.

This is better than blindly assigning cancelled regardless of the existing state.

A `RETURNING` clause can report which row was actually changed.

If no row qualifies, the update can return nothing.

That outcome may indicate the booking no longer exists in the expected state.

### 16.1 Beware `UPDATE ... FROM`

PostgreSQL allows an update to join other tables through a `FROM` clause.

This is convenient for bulk modifications.

But if the join produces multiple matches for one target row, the outcome can become unpredictable because the target may be associated with several candidate source rows.

Ensure the source relation produces at most one match per target row.

In production, always preview the affected rows and understand the transaction and locking consequences.

### 16.2 Upserts

PostgreSQL supports `INSERT ... ON CONFLICT`.

This lets an insert handle a uniqueness conflict by doing nothing or performing an update.

A customer-preferences table is a natural example.

If a preference row doesn't exist, insert it.

If it already exists, update its currency or locale.

The conflict target must correspond to an applicable uniqueness constraint or index.

An upsert can help enforce uniqueness under concurrency.

But it is not automatically a complete idempotency solution for operations such as charging payments or creating reservations.

Those require domain-specific guarantees.

## 17. Parameterized SQL and Application Code

Writing SQL independently does not mean constructing raw query strings through unsafe interpolation.

In a Node.js backend, application code should use parameterized queries.

For PostgreSQL's common `pg` client, values can be passed separately from the SQL text using placeholders such as `$1`, `$2`, and so on.

This prevents user-controlled values from being interpreted as executable SQL syntax.

It also separates the query's structure from its parameters.

Identifiers such as table names generally cannot be passed as ordinary value parameters. Dynamic identifiers require a different, carefully controlled approach.

### 17.1 Don't confuse parameterization with query correctness

A fully parameterized query can still have incorrect joins, wrong aggregation grain, or disastrous pagination behavior.

Parameterization addresses one important security boundary.

It does not prove that the query answers the business question.

## 18. Think Like a Reviewer

When reviewing unfamiliar SQL, use a compact sequence of questions.

What does one output row represent?

Which source rows qualify?

What is the cardinality of each join?

Can a join multiply financial amounts?

What happens when related rows are absent?

What does null mean in this calculation?

Is the ordering deterministic?

Could an update affect more rows than intended?

Does the query preserve the actual business invariant?

These questions matter before considering performance.

An engineer who can reason through them is much less dependent on an ORM or AI to construct SQL.

## 19. The Learning Objective Is Independent Composition

You do not need to memorize PostgreSQL's entire syntax reference.

Experienced engineers consult documentation.

The skill we're developing is knowing how to formulate the query, choose the correct relational operations, recognize potential mistakes, and verify the result.

An interviewer asks for a revenue ranking.

You identify the relevant tables.

You establish the grain.

You recognize the join-multiplication risk.

You construct intermediate aggregates.

You preserve zero-activity customers.

You sort deterministically.

Then you test the result against known data.

That is SQL fluency.

# Solutions and Discussion

### Solution 1 — The Join Multiplication

Joining two one-to-many relationships can produce a Cartesian multiplication within each booking.

Two line items multiplied by two payments can create four joined rows.

Aggregate payments at booking grain before joining them to other booking-level data.

### Solution 2 — The Disappearing Customer

The booking columns are null when a customer has no matching booking.

A `WHERE` condition requiring confirmed status removes those rows.

Filter bookings before the left join or place the status requirement in the join condition.

### Solution 3 — Counting Zero Activity

A left join preserves one customer row even without a matching booking.

`COUNT(*)` counts that preserved row.

`COUNT(booking_id)` counts only non-null matched booking IDs and therefore returns zero.

### Solution 4 — Refund Arithmetic

The successful refunds total €60.

The pending refund is excluded.

Net captured revenue is €240.

### Solution 5 — Grouping Versus Window Functions

Use grouping when you want to collapse multiple source rows into aggregate results, such as one row per customer.

Use a window function when you want to calculate information about related rows while preserving individual rows.

`PARTITION BY` defines the related row groups used by the window calculation.

### Solution 6 — The Missing Result

`SUM` returns null when no input values qualify.

Use `COALESCE(SUM(amount), 0)` when the business requires zero.

### Solution 7 — Pagination

Tied timestamps do not establish a unique order.

Add a unique tie-breaker, such as booking ID.

For deep sequential pagination, consider keyset pagination using the last returned timestamp and ID.

### Solution 8 — Conditional Updates

The condition prevents overwriting an unexpected current state.

`RETURNING` reports the rows changed and their resulting values.

It can help application code determine whether the expected transition occurred.

### Solution 9 — ORM Independence

Inspect the actual generated SQL and its join cardinalities.

Determine whether independent one-to-many relationships multiply rows before aggregation.

Changing ORM syntax doesn't necessarily correct the underlying relational mistake.

# The Mental Model Worth Keeping

Before writing a substantial SQL query, define the required output grain.

Then identify the source facts, their relationships, and the conditions that qualify them.

Use intermediate aggregates when joining independent one-to-many relationships.

Preserve missing entities deliberately.

Handle nulls, ties, and boundary conditions explicitly.

Finally, validate the query against known results.

**SQL fluency is the ability to translate business meaning into relational operations without accidentally changing that meaning.**

## 2. The Schema

Create a dedicated schema so the workshop does not conflict with unrelated tables.

```sql
DROP SCHEMA IF EXISTS cs350_lab CASCADE;
CREATE SCHEMA cs350_lab;

    customer_id integer PRIMARY KEY,
    name text NOT NULL

CREATE TABLE hotels (

CREATE TABLE bookings (

    hotel_id integer NOT NULL REFERENCES hotels(hotel_id),
    rooms integer NOT NULL CHECK (rooms > 0),
    nights integer NOT NULL CHECK (nights > 0),
    nightly_price_eur numeric(12,2) NOT NULL
        CHECK (nightly_price_eur >= 0)
);

CREATE TABLE payments (
    payment_id integer PRIMARY KEY,
    booking_id integer NOT NULL REFERENCES bookings(booking_id),
    status text NOT NULL
        CHECK (status IN ('captured', 'failed', 'pending')),
    amount_eur numeric(12,2) NOT NULL
        CHECK (amount_eur > 0)
);

CREATE TABLE refunds (
    refund_id integer PRIMARY KEY,
    payment_id integer NOT NULL REFERENCES payments(payment_id),
    status text NOT NULL
        CHECK (status IN ('succeeded', 'pending', 'failed')),
    amount_eur numeric(12,2) NOT NULL
        CHECK (amount_eur > 0)
);

CREATE TABLE customer_preferences (
    customer_id integer PRIMARY KEY REFERENCES customers(customer_id),
    currency text NOT NULL,
    updated_at timestamptz NOT NULL DEFAULT now()
);
```

### Important schema assumptions

The fixture deliberately separates booked line-item value from captured payments.

A booking can exist without a successful payment.

A booking can have several captured payments.

A payment can have several refunds.

The schema demonstrates basic relational constraints, but it is not a production-grade reservation or accounting system.

For example, it does not enforce that total successful refunds never exceed captured amounts.

Nor does it model every real payment lifecycle state.

Those are important business invariants, but they are outside the immediate purpose of this SQL-composition lab.

# Reference Solutions and Discussion

## Solution 1 — Relevant Bookings

Use an explicit half-open reporting window and deterministic ordering.

```sql
SELECT
    b.booking_id,
    c.name AS customer_name,
    b.booked_at,
    b.status
FROM cs350_lab.bookings b
JOIN cs350_lab.customers c
    ON c.customer_id = b.customer_id
WHERE b.status = 'confirmed'
  AND b.booked_at >= TIMESTAMPTZ '2026-07-31 00:00:00+00'
  AND b.booked_at <  TIMESTAMPTZ '2026-10-29 00:00:00+00'
ORDER BY
    b.booked_at DESC,
    b.booking_id DESC;
```

Seven bookings qualify.

The tie-breaker ensures that bookings sharing a timestamp have a deterministic relative order.

## Solution 2 — Customers with Zero Activity

First filter qualifying bookings in a CTE, then left join customers to them.

```sql
WITH qualifying AS (
    SELECT booking_id, customer_id
    FROM cs350_lab.bookings
    WHERE status = 'confirmed'
      AND booked_at >= TIMESTAMPTZ '2026-07-31 00:00:00+00'
      AND booked_at <  TIMESTAMPTZ '2026-10-29 00:00:00+00'
)
SELECT
    c.customer_id,
    c.name,
    COUNT(q.booking_id) AS booking_count
FROM cs350_lab.customers c
LEFT JOIN qualifying q
    ON q.customer_id = c.customer_id
GROUP BY c.customer_id, c.name
ORDER BY c.customer_id;
```

The left join preserves customers without qualifying bookings.

Counting `q.booking_id` returns zero for unmatched customers.

## Solution 3 — Booked Value and Captured Payments

First calculate booked value by booking.

```sql
SELECT
    b.booking_id,
    SUM(
        i.rooms * i.nights * i.nightly_price_eur
    ) AS booked_value
FROM cs350_lab.bookings b
JOIN cs350_lab.booking_items i
    ON i.booking_id = b.booking_id
WHERE b.status = 'confirmed'
  AND b.booked_at >= TIMESTAMPTZ '2026-07-31 00:00:00+00'
  AND b.booked_at <  TIMESTAMPTZ '2026-10-29 00:00:00+00'
GROUP BY b.booking_id
ORDER BY b.booking_id;
```

Next calculate captured payments independently.

```sql
SELECT
    p.booking_id,
    SUM(p.amount_eur) AS captured_amount
FROM cs350_lab.payments p
JOIN cs350_lab.bookings b
    ON b.booking_id = p.booking_id
WHERE p.status = 'captured'
  AND b.status = 'confirmed'
  AND b.booked_at >= TIMESTAMPTZ '2026-07-31 00:00:00+00'
  AND b.booked_at <  TIMESTAMPTZ '2026-10-29 00:00:00+00'
GROUP BY p.booking_id
ORDER BY p.booking_id;
```

Booking 103 has two items and two captured payments.

If you join both child tables directly, each payment can appear once for each item.

Pre-aggregating by booking prevents this multiplication.

## Solution 4 — Revenue Ranking

This is the most important reference solution.

It deliberately separates the different financial relationships before joining them.

```sql
WITH qualifying_bookings AS (
    SELECT
        booking_id,
        customer_id
    FROM cs350_lab.bookings
    WHERE status = 'confirmed'
      AND booked_at >= TIMESTAMPTZ '2026-07-31 00:00:00+00'
      AND booked_at <  TIMESTAMPTZ '2026-10-29 00:00:00+00'
),

captured_by_booking AS (
    SELECT
        p.booking_id,
        SUM(p.amount_eur) AS captured_eur
    FROM cs350_lab.payments p
    JOIN qualifying_bookings b
        ON b.booking_id = p.booking_id
    WHERE p.status = 'captured'
    GROUP BY p.booking_id
),

refunded_by_booking AS (
    SELECT
        p.booking_id,
        SUM(r.amount_eur) AS refunded_eur
    FROM cs350_lab.refunds r
    JOIN cs350_lab.payments p
        ON p.payment_id = r.payment_id
    JOIN qualifying_bookings b
        ON b.booking_id = p.booking_id
    WHERE r.status = 'succeeded'
      AND p.status = 'captured'
    GROUP BY p.booking_id
),

booking_financials AS (
    SELECT
        b.booking_id,
        b.customer_id,
        COALESCE(cp.captured_eur, 0) AS captured_eur,
        COALESCE(rp.refunded_eur, 0) AS refunded_eur
    FROM qualifying_bookings b
    LEFT JOIN captured_by_booking cp
        ON cp.booking_id = b.booking_id
    LEFT JOIN refunded_by_booking rp
        ON rp.booking_id = b.booking_id
)

SELECT
    c.customer_id,
    c.name,
    COUNT(b.booking_id) AS confirmed_bookings,
    COALESCE(SUM(b.captured_eur), 0) AS captured_eur,
    COALESCE(SUM(b.refunded_eur), 0) AS refunded_eur,
    COALESCE(
        SUM(b.captured_eur - b.refunded_eur),
        0
    ) AS net_revenue_eur
FROM cs350_lab.customers c
LEFT JOIN booking_financials b
    ON b.customer_id = c.customer_id
GROUP BY c.customer_id, c.name
ORDER BY
    net_revenue_eur DESC,
    c.customer_id ASC
LIMIT 5;
```

### Expected detailed result

| Customer | Bookings | Captured | Refunded | Net |
|---|---:|---:|---:|---:|
| Alice | 2 | €500 | €50 | €450 |
| Bob | 2 | €380 | €105 | €275 |
| Erin | 2 | €120 | €0 | €120 |
| Cara | 1 | €100 | €20 | €80 |
| Dan | 0 | €0 | €0 | €0 |

Fay also has zero revenue but appears after Dan when sorted by customer ID.

### Why this solution is reliable

Every financial CTE produces at most one row per booking.

The final left join preserves all customers.

The captured-payment calculation excludes failed and pending payments.

The refund calculation includes only successful refunds associated with captured payments.

The reporting window is applied to qualifying bookings.

The final order has a deterministic tie-breaker.

The result is built from explicit intermediate meanings rather than one enormous financial join.

Use `FILTER` to count different booking statuses independently.

```sql
        AS confirmed_count,
    COUNT(b.booking_id)
        FILTER (WHERE b.status = 'cancelled')
        AS cancelled_count,
    COUNT(b.booking_id)
        FILTER (WHERE b.status = 'pending')
        AS pending_count

```

```sql
    FROM cs350_lab.bookings b
```

## Solution 7 — Latest Confirmed Booking

Use a window function to number confirmed bookings within each customer partition.

```sql
WITH ranked AS (
    SELECT
        b.booking_id,
        b.customer_id,
        b.booked_at,
        ROW_NUMBER() OVER (
            PARTITION BY b.customer_id
            ORDER BY b.booked_at DESC, b.booking_id DESC
        ) AS position
    FROM cs350_lab.bookings b
    WHERE b.status = 'confirmed'
)
SELECT
    c.customer_id,
    c.name,
    r.booking_id,
    r.booked_at
FROM ranked r
JOIN cs350_lab.customers c
    ON c.customer_id = r.customer_id
WHERE r.position = 1
ORDER BY c.customer_id;
```

The `PARTITION BY` clause establishes one independent sequence per customer.

The ordering determines which booking is considered newest.

### PostgreSQL-specific alternative

`DISTINCT ON` can express the same requirement compactly.

```sql
SELECT DISTINCT ON (b.customer_id)
    c.customer_id,
    c.name,
    b.booking_id,
    b.booked_at
FROM cs350_lab.bookings b
JOIN cs350_lab.customers c
    ON c.customer_id = b.customer_id
WHERE b.status = 'confirmed'
ORDER BY
    b.customer_id,
    b.booked_at DESC,
    b.booking_id DESC;
```

Here, the `ORDER BY` determines which row is retained for each customer.

Both approaches are valid.

The window-function version is more portable across database systems.

## Solution 8 — Hotel Popularity

Aggregate room-nights from confirmed booking items, then preserve all hotels through a left join.

```sql
WITH hotel_activity AS (
    SELECT
        i.hotel_id,
        COUNT(DISTINCT b.booking_id) AS booking_count,
        SUM(i.rooms * i.nights) AS room_nights
    FROM cs350_lab.booking_items i
    JOIN cs350_lab.bookings b
        ON b.booking_id = i.booking_id
    WHERE b.status = 'confirmed'
      AND b.booked_at >= TIMESTAMPTZ '2026-07-31 00:00:00+00'
      AND b.booked_at <  TIMESTAMPTZ '2026-10-29 00:00:00+00'
    GROUP BY i.hotel_id
)
SELECT
    h.hotel_id,
    h.name,
    COALESCE(a.booking_count, 0) AS booking_count,
    COALESCE(a.room_nights, 0) AS room_nights
FROM cs350_lab.hotels h
LEFT JOIN hotel_activity a
    ON a.hotel_id = h.hotel_id
ORDER BY
    room_nights DESC,
    h.hotel_id;
```

The result is Canal House with six room-nights, Hotel Aurora with five, and Mountain Pines with zero.

The distinct booking count guards against multiple line items for the same hotel within a booking.

## Solution 9 — Keyset Pagination

First retrieve the newest three confirmed bookings.

```sql
SELECT
    booking_id,
    customer_id,
    booked_at
FROM cs350_lab.bookings
WHERE status = 'confirmed'
ORDER BY booked_at DESC, booking_id DESC
LIMIT 3;
```

The first page ends at a particular `(booked_at, booking_id)` tuple.

Use that tuple as the cursor for the next page.

For the fixture, the first page ends with booking 103.

```sql
SELECT
    booking_id,
    customer_id,
    booked_at
FROM cs350_lab.bookings
WHERE status = 'confirmed'
  AND (booked_at, booking_id) <
      (
        TIMESTAMPTZ '2026-10-11 10:00:00+00',
        103
      )
ORDER BY booked_at DESC, booking_id DESC
LIMIT 3;
```

This works because both fields are ordered descending and the tuple comparison establishes the next page's boundary.

A production cursor should encode the relevant ordering values safely rather than accepting arbitrary SQL fragments.

If booking timestamps or other ordering fields are mutable, the pagination contract needs additional consideration.

## Solution 10 — Conditional Update

Perform the update inside a transaction.

```sql
BEGIN;

UPDATE cs350_lab.bookings
SET status = 'cancelled'
WHERE booking_id = 110
  AND status = 'pending'
RETURNING booking_id, status;

UPDATE cs350_lab.bookings
SET status = 'cancelled'
WHERE booking_id = 110
  AND status = 'pending'
RETURNING booking_id, status;

ROLLBACK;
```

The first update returns the changed booking.

The second returns no rows because the status no longer matches the condition.

Rolling back restores the original fixture.

## Solution 11 — Upsert

Use the customer ID as the conflict target.

```sql
BEGIN;

INSERT INTO cs350_lab.customer_preferences (
    customer_id, currency
)
VALUES (1, 'EUR')
ON CONFLICT (customer_id)
DO UPDATE SET
    currency = EXCLUDED.currency,
    updated_at = now()
RETURNING *;

INSERT INTO cs350_lab.customer_preferences (
    customer_id, currency
)
VALUES (1, 'GBP')
ON CONFLICT (customer_id)
DO UPDATE SET
    currency = EXCLUDED.currency,
    updated_at = now()
RETURNING *;

ROLLBACK;
```

`EXCLUDED` refers to the row proposed for insertion.

The uniqueness constraint on customer ID ensures that only one preference row can exist per customer.

The second statement updates the existing row rather than inserting a duplicate.

## Solution 12 — Review Principles

The strongest solution is one whose intermediate relations have clearly defined grains.

The captured-payment aggregate is one row per booking.

The refund aggregate is one row per booking.

The booking financial result is one row per booking.

The customer report is one row per customer.

Financial values should not multiply because unrelated child relationships were joined before aggregation.

A historical as-of report would require appropriate financial event timestamps or an immutable accounting ledger, not merely the current statuses stored in this simplified fixture.

Performance optimization should begin only after correctness is established.

In CS350-L02, the first evidence will be the actual query plan and its measured work.

# Dense Cheatsheet — Interview Glance Card

*Screen-only revision card. The fenced material can be skipped by voice readers.*

```text
CS350-L01 — SQL FLUENCY
================================================

FIRST QUESTION
--------------
What does ONE OUTPUT ROW represent?

Possible grains:
- customer
- booking
- booking item
- payment
- refund

JOINS
-----
INNER JOIN:
  only matching combinations

LEFT JOIN:
  preserve left rows, nulls on right

One-to-many joins multiply rows.

Two independent one-to-many joins can
multiply facts against one another.

Avoid summing financial values after
uncontrolled fanout.

FILTERING
---------
WHERE:
  filter source rows

GROUP BY:
  define aggregate groups

HAVING:
  filter aggregated groups

LEFT JOIN GOTCHA
----------------
WHERE child.status = 'confirmed'
can remove unmatched parent rows.

Filter children before joining or place
the condition in the ON clause.

COUNT
-----
COUNT(*) counts result rows.
COUNT(column) counts non-null values.
COUNT(DISTINCT column) counts unique
non-null values.

For unmatched left join:
COUNT(*) may be 1.
COUNT(child.id) is 0.

NULL
----
NULL != 0
NULL != false
NULL is missing/unknown information

Use IS NULL / IS NOT NULL.
Use COALESCE for explicit fallback.

SUM over no qualifying values -> NULL
COUNT over no values -> 0

AGGREGATES
----------
SUM(amount)
AVG(amount)
MIN(value)
MAX(value)
COUNT(*)

Conditional:
COUNT(*) FILTER (WHERE condition)

CTEs
----
WITH name AS (
  SELECT ...
)
SELECT ...
FROM name;

Give each CTE one clear responsibility.
Define the grain of its output.

CTE != guaranteed temporary table.
Planner may inline or materialize.

WINDOW FUNCTIONS
----------------
ROW_NUMBER() OVER (
  PARTITION BY customer_id
  ORDER BY booked_at DESC, booking_id DESC
)

Preserves individual rows.

ROW_NUMBER:
  unique sequential positions

RANK:
  ties share rank, gaps follow

DENSE_RANK:
  ties share rank, no gaps

Explicit frames matter for running sums.

EXISTS
------
EXISTS:
  at least one matching row

NOT EXISTS:
  no matching rows

Often clearer than joins when only
existence matters.

NOT IN can surprise with NULL values.

PAGINATION
----------
Always define deterministic order.

ORDER BY created_at DESC, id DESC

OFFSET:
  easy arbitrary pages
  deep skips can be expensive

KEYSET:
  use last returned sort tuple

WHERE (created_at, id) < (:time, :id)

Use matching DESC order.
Cursor must represent full ordering.

MUTATIONS
---------
UPDATE ... WHERE expected_state
RETURNING ...

Guard transitions with conditions.
Check affected rows.

INSERT ... ON CONFLICT:
  insert or handle unique conflict

EXCLUDED:
  proposed inserted row

UPDATE ... FROM:
  avoid multiple source matches
  for one target row.

PARAMETERIZATION
----------------
Use $1, $2, ... for values.
Avoid string interpolation of user input.

Parameterization != logical correctness.

FINANCIAL REPORTING
-------------------
1. Identify qualifying bookings.
2. Aggregate captured payments by booking.
3. Aggregate successful refunds by booking.
4. Combine booking-level amounts.
5. Aggregate by customer.
6. Preserve zero-activity customers.
7. Apply deterministic ordering.

Booked value != captured revenue.
Pending refund != successful refund.

REVIEW CHECKLIST
----------------
What is the output grain?
Which rows qualify?
What does each join multiply?
What happens when there is no match?
Can nulls affect the calculation?
Are statuses handled correctly?
Is ordering deterministic?
Can an update touch unintended rows?
Can I verify against known examples?

CORE PRINCIPLE
--------------
Correct meaning first.
Readable relational operations second.
Execution performance third.
```
