# CS330 — Course Examination EX01: Data That Must Stay True

**Course:** Relational Databases and Transactions · **Coverage:** CS330-L01–L03 and selected interview-relevant extensions  
**Audience:** Practical senior full-stack/backend · **Use:** Attempt any number of questions before reading Part II.  

You aren't being examined on remembering PostgreSQL command-line syntax. Explain what you believe the database is doing, which invariant matters, and how you'd verify a performance or correctness claim. Multiple designs may be valid.

# Part I — Questions

## Round A — Make the data model tell the truth

### Q01 — The renamed hotel changed an old invoice
A travel product stores each booking's hotel name by reading the current hotel table whenever an invoice is rendered. The hotel gets renamed, and invoices from two years ago now show the new name. What would you change in the data model, and isn't this technically duplication?

### Q02 — A schema with no obvious error
A reservation has a `hotel_id` and a `room_id`. Both reference existing rows, but sometimes the room belongs to a different hotel. The database says the references are valid. What does this tell you about the schema, and how can you protect the stronger rule?

### Q03 — Two profiles claim the same external identity
You import user accounts from another service. Two concurrent requests try to create different local users with the same external customer identifier. Both succeed despite your `SELECT`-before-`INSERT` check. What should own the guarantee?

### Q04 — A column for everything
A developer wants to put order items, taxes, and shipping history into a single JSON column inside `orders` to avoid joins. Would you accept that design? What questions would determine your decision?

## Round B — The query that surprises you

### Q05 — The index is there, but performance isn't
A query searches for orders in one tenant, sorts by `created_at DESC`, and returns 20 records. It becomes painfully slow as the table grows even though both `tenant_id` and `created_at` have indexes. What would you inspect and potentially change?

### Q06 — Page 10,000 is painfully expensive
The first page of a sorted activity feed loads instantly; the 10,000th page takes seconds. The UI uses `LIMIT 20 OFFSET 199980`. Why might the database do substantial work to return only twenty rows? What alternatives would you propose?

### Q07 — The join that multiplied a report
A query joins bookings to payments and booking items. A booking with three items and two payments produces six rows, and the report overcounts revenue. Is the database malfunctioning? How would you fix the query or report design?

### Q08 — The index sometimes loses to a scan
A query planner uses an index for a tenant with 100 rows but chooses a sequential scan for a tenant with hundreds of thousands of rows. A teammate demands the database always use the index. How would you respond?

### Q09 — Fast yesterday, slow today
A production query regresses without a code deployment. What evidence would you collect before creating another index or buying a larger database instance?

## Round C — Concurrency and evolution

### Q10 — Last room sold twice
Two transactions each read available inventory and independently decide a reservation is allowed. Both commit. Explain how that can happen and what practical changes would ensure the invariant holds.

### Q11 — Two doctors, one on call
Two employees are currently on call. Each transaction checks that someone else is on call and removes its own employee from duty. Both commit; now nobody is on call. Why can this occur even without updating the same row, and how might you prevent it?

### Q12 — The payment happens inside a transaction
A teammate proposes opening a database transaction, calling a payment provider, and committing only if the provider confirms success. Why can this design become dangerous or misleading? How would you shape the workflow instead?

### Q13 — A migration while old and new code run together
You must replace a single `customer_name` field with `first_name` and `last_name`, but application instances are rolled out gradually. How do you migrate without breaking old instances or losing data?

### Q14 — The deadlock nobody expected
Two request handlers update account A and account B in different orders. They occasionally fail with a deadlock error. Is it necessarily a database bug? What should the application do?

# Part II — Model Answers and Reasoning

### A01 — The renamed hotel changed an old invoice
An invoice is a historical record, not a dynamic report on the current hotel entity. Store the facts legally/business-relevantly fixed at booking or invoice time: hotel display name, price, taxes, address where required, and applicable terms, while retaining a reference to the current hotel entity. This is deliberate denormalization or snapshotting, not an accidental update anomaly. Normalize current entities to avoid inconsistent live facts, and snapshot historical facts because their meaning is time-dependent. Decide which fields must remain immutable, how adjustments are represented, and how invoice versions are audited. A database design expresses the business semantics of time, not merely how to minimize duplicate strings.

### A02 — A schema with no obvious error
Two independent foreign keys only prove that both referenced rows exist; they do not prove that the chosen room belongs to the chosen hotel. If the business rule requires this relationship, use a composite foreign key or a schema that derives hotel ownership from the room rather than accepting two conflicting sources of truth. For example, a reservation might reference a room ID and infer its hotel, or use a composite `(hotel_id, room_id)` reference to a unique pair. Application validation improves user-facing errors but does not replace a durable database constraint when concurrency or bypassing code paths matter. Ask whether rooms can move between hotels and how history should behave.

### A03 — Two profiles claim the same external identity
A pre-insert read is racy: both sessions can observe no matching row before either inserts. If the identifier must be unique within a provider/tenant, encode that in a unique constraint or unique index on the correct scope, such as `(provider, external_customer_id)`. Then handle constraint violations as an expected concurrency outcome, returning an existing identity or a sensible conflict. Also decide how account merging and provider identity changes work. Database constraints protect invariants regardless of which service, background job, or administrator performs the write. The check can remain for friendliness, but it isn't the authoritative guarantee.

### A04 — A column for everything
JSON can be appropriate for a bounded, self-contained, low-queryability snapshot or provider-specific metadata. It becomes expensive when embedded items need independent filtering, constraints, aggregation, reference integrity, or high-frequency updates. Ask about access patterns, cardinality, growth, update frequency, cross-item rules, and reporting. A relational design for order items/payments typically gives stronger constraints and straightforward joins; preserving an immutable source payload in JSON alongside normalized operational fields can be reasonable. The relevant question isn't whether joins are bad—it's whether the chosen storage layout represents the business relationships and anticipated queries cleanly.

### A05 — The index is there, but performance isn't
Separate indexes do not automatically produce an efficient ordered, tenant-scoped scan. Inspect the actual plan with `EXPLAIN (ANALYZE, BUFFERS)` on safe representative data, checking scanned rows, sort work, estimates, and I/O. A composite index such as `(tenant_id, created_at DESC, id DESC)` may allow an ordered walk of one tenant without a large sort; the exact columns depend on predicates and return requirements. Add a deterministic tie-breaker for pagination. An index can still be unhelpful when selectivity is low or the query needs many heap fetches. Validate performance with real distributions before declaring victory.

### A06 — Page 10,000 is painfully expensive
OFFSET doesn't mean jump directly to the last twenty matching records. The engine may still find, order, and discard roughly 199,980 earlier rows, so deep pages cost more. For feeds and infinite scroll, keyset/cursor pagination uses a stable ordering such as `(created_at DESC, id DESC)` and a condition continuing after the last seen pair. That lets a suitable index seek into the next page. It changes navigation semantics (jump to arbitrary page is harder), and concurrent inserts can affect what a user sees. If exact random page numbers are essential, accept the trade-off or redesign the product requirement; don't assume a bigger OFFSET is free.

### A07 — The join that multiplied a report
The joins form a multiplicative relationship: three item rows times two payment rows yield six joined rows per booking. SQL is doing what the join describes. Aggregate payments and items separately at booking granularity before combining, or use subqueries/CTEs with explicit grouping, depending on the desired measures. `DISTINCT` is not a universal fix; it may conceal a flawed grain and break legitimate duplicates. Define what each output row represents and which table owns the monetary fact. Be especially careful with refunds, partial captures, and item quantities. Always verify totals against small hand-calculated examples.

### A08 — The index sometimes loses to a scan
An index is an alternative access path with its own costs. When many rows match, hopping between index and table pages can cost more than a sequential scan, especially if reads aren't well localized. The planner estimates selectivity and cost from statistics, which can also be stale or misleading. Compare estimated versus actual rows, buffers, index coverage, and predicate shapes. Don't force an index out of instinct; measure. Sometimes the correct solution is a better index, statistics, partitioning, a changed query, or even accepting the sequential scan. Performance is about work avoided, not the presence of an index in the execution plan.

### A09 — Fast yesterday, slow today
Collect the exact SQL/query parameters, execution plan, estimates versus actual row counts, indexes, table size and data distribution, locks, active transactions, CPU/I/O pressure, and changes in traffic or parameter mix. Look for table/index bloat, stale statistics, new high-cardinality tenants, blocking transactions, or different prepared-plan behavior. Determine whether it's a regression in planning, volume, contention, or downstream resource saturation. Compare representative slow and fast executions. Creating another index without evidence may improve one query while slowing writes and consuming resources. The first step is to locate the expensive operation and explain why it suddenly became expensive.

### A10 — Last room sold twice
If both transactions read the same available count and make the decision before synchronized writes, they may violate the invariant under the chosen isolation semantics or application pattern. The fix is to make the decision and state transition atomic: a conditional `UPDATE ... WHERE available > 0` that decrements and reports whether a row changed, or an appropriate row lock/serializable transaction with retries. Ensure a reservation identity so retries don't consume multiple units. Business correctness depends on the write actually enforcing availability, not just a check in application memory. Test the operation with concurrent requests rather than only single-threaded unit tests.

### A11 — Two doctors, one on call
This is the classic write-skew shape: the transactions read a shared invariant but update different rows, so no direct same-row write conflict necessarily occurs. Snapshot-like isolation can permit both decisions to commit. You can use serializable isolation with correct retry logic, explicitly lock a shared authoritative row protecting the invariant, or model the operation as an atomic state transition with a suitable constraint where feasible. The important distinction is that merely preventing lost updates doesn't protect every multi-row rule. Ask which invariant must survive concurrent decisions and what database mechanism actually enforces it.

### A12 — The payment happens inside a transaction
A database transaction cannot roll back an external payment provider's successful charge. Keeping it open during a slow remote request may hold locks and connections, worsen contention, and still produce an ambiguous outcome if the response is lost. Instead persist a durable order/payment intent, call the provider with an idempotent operation identity, record results through carefully scoped local transactions, and reconcile unknown states. Often a state machine and asynchronous workflow are simpler to reason about than pretending a distributed payment belongs to the database transaction. A transaction protects local database changes; it isn't a magical cross-service undo button.

### A13 — A migration while old and new code run together
Use an expand-and-contract rollout. First add new nullable columns and deploy code that can read both forms while writing both where necessary. Backfill existing rows in manageable batches, verify completeness and consistency, then move reads to the new columns. Only after all old application versions and asynchronous workers are retired should you remove the old field and enforce new non-null or other constraints. Decide how to parse ambiguous names—some cannot be reliably split automatically. Coordinate the deployment and migration sequence, and measure/rollback where feasible. Breaking schema changes should not assume an atomic fleet-wide rollout.

### A14 — The deadlock nobody expected
Deadlocks can occur during normal concurrent transactions: each session holds resources the other needs, so the database chooses one as a victim. Update shared records in a consistent order where possible, shorten transactions, and ensure indexes reduce unnecessary locking. The application should recognize the database's retryable deadlock error and retry the **whole transaction** within a bounded policy, not blindly replay one statement after the transaction was aborted. Preserve idempotency for any external side effects and add telemetry if deadlocks become frequent. A small rate of conflict can be normal; escalating frequency can indicate poor lock ordering or a hot resource.

## Closing perspective

Strong database answers start with **the data invariant and the real query plan**. Transactions, constraints, indexes, and schemas are tools for keeping those two things honest—not vocabulary tests.
